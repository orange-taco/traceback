Delivery · source to running container

두 번 검증하고, 한 번 만든 이미지를 승격합니다

feature PR은 코드를 검증하고, development push가 이미지를 ECR에 올립니다. main은 새 이미지를 만들지 않고 development에서 배포에 성공한 digest를 사용합니다. 각 단계를 눌러 실행 조건과 실제 코드를 볼 수 있습니다. 코드 상자는 핵심 부분을 축약한 것이며 원본 파일로 이동할 수 있습니다.

도구 버전 · 외부 저장소Action 커밋 SHA

uses: astral-sh/setup-uv@…의 SHA는 CI가 실행할 외부 Action 코드입니다. 우리 앱 버전이 아닙니다. version: 0.10.4는 설치할 uv 프로그램 버전입니다.

소스 버전 · TRACEBACK앱 커밋 SHA

GitHub push의 github.sha입니다. development 배포에서는 이 값을 ECR 이미지 태그로 사용합니다. 운영에서는 릴리스 merge commit의 두 번째 부모가 개발 원본 SHA입니다.

이미지 내용 · ECRimage digest

@sha256:…은 빌드된 이미지 내용을 식별합니다. 개발 EC2와 운영 EC2가 이 동일한 digest를 실행합니다.

feature→ PR →development→ PR →main
동일 image digestdevelopment ECR image → production EC2 · 운영에서 재빌드 없음

두 환경이 공통으로 실행하는 EC2 단계

04 · DATABASE설정 검사·migrate운영 override는 로컬 DB·포트·볼륨을 제거하고 외부 DB URL을 씁니다.코드와 설명

두 Compose 파일을 병합해 설정을 검사합니다. 운영 override의 !reset이 개발 DB 서비스·호스트 포트·bind volume을 제거합니다. 이어 서버의 .env에 지정된 DB를 대상으로 migration을 실행합니다. DB URL 자체는 Dockerfile이 아니라 서버 환경 파일에 있습니다.

현재 workflow·이미지 빌드·로컬 smoke는 검증됐지만 실제 AWS 배포는 아직 아닙니다. GitHub development Environment에는 배포 변수 4개가 아직 등록되지 않아 원격 배포가 aws-region 단계에서 멈췄습니다. 이 healthcheck는 컨테이너 내부 확인이며 외부 reverse proxy/TLS와 자동 rollback은 별도입니다.

파일을 실행 순서대로 읽는 지도

현재 구현된 서버 코드와 CI/CD 파일을 책임별로 묶었습니다. 각 상자를 열면 입력, 핵심 판단, 결과를 축약한 코드와 연결할 수 있습니다. 정확한 전체 코드는 각 파일 링크에서 확인하세요. Catalog 이후 도메인은 아직 구현되지 않았습니다.

브라우저 요청→URL · middleware→allauth 또는 accounts view→service · provider · DB

① 서버가 요청을 처리하는 코드

먼저 입구와 설정을 읽고, 인증 분기와 데이터 변경을 따라가면 됩니다. Framework는 allauth·Django가 소유하고, TRACEBACK는 이 저장소의 코드입니다.

TRACEBACK · entryURL과 ASGI 입구

config/urls.py가 /_allauth/를 라이브러리에, /accounts/를 프로젝트 view와 allauth에 연결합니다. config/asgi.py는 Gunicorn이 부르는 앱 객체입니다.

path("accounts/", include(("apps.accounts.urls", "accounts"), namespace="accounts"))
path("_allauth/", include("allauth.headless.urls"))
application = get_asgi_application()

요청 URL이 어느 코드로 가는지 여기서 먼저 확인합니다. commerce API는 아직 추가되지 않았습니다.

urls.py · asgi.py
TRACEBACK · configuration공통 설정과 환경 차이

base.py가 DB URL, 세션 인증, allauth, Kakao, 공통 오류 형식을 묶습니다. local/development/production/test.py가 환경별 차이를 정합니다.

DATABASES = {"default": dj_database_url.parse(
    os.environ["TRACEBACK_DATABASE_URL"], ...)}
"EXCEPTION_HANDLER": "apps.core.exception_handlers.custom_exception_handler"

local은 console mail, test는 임시 SQLite/메일 메모리 저장소, production은 보안 쿠키와 proxy HTTPS 설정입니다. AWS 실행값은 각 EC2의 /opt/traceback/.env에서 들어옵니다.

base.py · local.py · development.py · production.py · test.py
Framework + TRACEBACK · authenticationallauth와 소셜 정책

가입·로그인·이메일 인증·세션은 allauth Headless가 수행합니다. SocialAccountAdapter는 새 Kakao 로그인에 검증된 이메일을 요구하고 연결 해제 전에 원격 unlink를 수행합니다.

if not any(address.verified for address in sociallogin.email_addresses):
    raise ProviderException(...)
unlink_kakao_user(account.uid)

두 메서드가 다른 시점에 호출됩니다. 첫 줄은 새 소셜 로그인 전, unlink는 allauth의 연결 해제 검증 때입니다. 실패하면 로컬 연결을 유지합니다.

USERNAME_FIELD = "email"

스키마는 apps/accounts/migrations/에 순서대로 기록됩니다. allauth의 EmailAddress, SocialAccount, UserSession은 라이브러리 모델입니다.

TRACEBACK + Kakao · external call원격 unlink와 계정 삭제

providers.py는 Admin Key로 Kakao unlink API를 호출하고 응답 UID를 확인합니다. services.py는 원격 해제 성공 후 DB transaction에서 사용자를 익명화하고 세션을 종료합니다.

unlink_kakao_user(account.uid)
with transaction.atomic():
    locked_user = User.objects.select_for_update().get(...)
    locked_user.is_active = False

Kakao 오류면 로컬 삭제를 시작하지 않습니다. Kakao -101은 이미 해제된 상태로 성공 처리합니다. 세션 종료는 DB transaction 뒤에 실행됩니다.

providers.py · services.py
TRACEBACK · HTTP boundary계정 API와 공통 응답

views.py는 인증 메일 재전송과 계정 삭제 요청을 받습니다. core middleware는 요청 ID를 만들고, exception handler는 오류를 code/message/details/request_id로 정리합니다.

POST /accounts/email/verify/resend
DELETE /accounts/delete
{"code": ..., "message": ..., "details": ..., "request_id": ...}

재전송은 계정 존재 여부를 응답으로 노출하지 않습니다. detail 필드의 목록형 검증 오류는 details.detail에 남습니다. 공통 페이지네이션은 최대 100개입니다.

apps/accounts/tests는 계정 모델·Kakao 연동·API·비밀번호 변경을, apps/core/tests는 요청 ID·오류 형식·페이지네이션·권한을 검증합니다.

CI의 test job은 PostgreSQL 서비스에서 검사·migration·pytest를 실행합니다. 로컬 테스트의 SQLite 성공만으로 원격 배포 성공을 뜻하지 않습니다.

accounts/tests · core API 테스트 · ci.yml

② 변경을 검증하고 서버에 보내는 코드

CI/CD는 브랜치별로 시작 조건이 다릅니다. 여기의 Action SHA는 외부 도구 버전이며, ECR 태그에 쓰는 앱 커밋 SHA와 구분하세요.

ci.yml→개발 빌드·배포→ECR digest→운영 승격·배포

개발과 운영 배포는 모두 deploy-ec2.sh를 호출합니다. 두 배포가 서로 직접 호출하는 구조는 아닙니다.

GitHub Actions · event gateci.yml: 언제 무엇을 검사하나

모든 PR과 development/main push에서 quality·test를 실행합니다. main 대상 PR은 출발 브랜치와 production 컨테이너 smoke를 추가 검사합니다. CD는 push와 두 job 성공 뒤에만 시작합니다.

on: pull_request | push(development, main)
deploy-development: if push && development
deploy-production: if push && main
needs: [quality, test]

uses: ...@긴_SHA는 checkout/setup-uv Action의 코드를 고정합니다. version: "0.10.4"는 uv 자체 버전입니다. PR의 quality/test가 통과해도 배포하지 않습니다.

ci.yml 원본
GitHub Actions + AWS · publish개발 이미지 빌드와 재사용

deploy-development.yml이 OIDC 역할을 인수하고 ECR immutable tag를 확인합니다. 동일 앱 커밋의 이미지가 있으면 digest를 재사용하고, 없을 때만 빌드합니다.

imageTag=$GITHUB_SHA
if: steps.existing.outputs.digest == ''
target: production
push: true

빌드 결과는 registry/repository@sha256:…로 다음 job에 전달됩니다. ECR/SSM 권한은 GitHub의 development Environment와 AWS IAM 설정에 달려 있습니다.

deploy-development.yml 원본
GitHub Actions + AWS · promotion운영은 동일 이미지 승격

deploy-production.yml은 main 릴리스 merge commit의 두 번째 부모를 개발 원본 SHA로 읽습니다. 그 SHA의 개발 EC2 배포 성공을 GitHub에서 확인하고 ECR digest를 가져옵니다.

source_sha="$(git rev-parse --verify HEAD^2)"
test "$(git rev-parse --verify HEAD^1)" = "$BEFORE_SHA"
gh run list ... --commit "$source_sha"
aws ecr describe-images ... imageTag=$source_sha

성공 기록·immutable ECR 태그·digest 중 하나라도 없으면 운영 배포를 멈춥니다. 이 workflow에는 Docker build 단계가 없습니다. Production Environment 승인 규칙은 GitHub에서 별도로 설정해야 합니다.

deploy-production.yml 원본
Runner + EC2 · remote commanddeploy-ec2.sh: 서버에서 하는 일

digest URI를 검사하고 SSM 명령을 EC2에 보냅니다. EC2는 ECR login/pull → 이미지 속 Compose 추출 → config 검사 → migrate → app 교체를 실행합니다.

aws ssm send-command ...
docker pull "$APP_IMAGE"
docker compose ... run --rm app python manage.py migrate --noinput
docker compose ... up -d --no-build --wait app

runner는 최대 10분 상태를 폴링합니다. migration 실패 시 새 app 시작 전에 중단하지만, 이미 적용된 DB 변경을 자동 복구하지는 않습니다.

deploy-ec2.sh 원본
Docker · image buildDockerfile: 한 소스, 두 target

공통 Python/uv base에서 개발 의존성과 운영 의존성을 분리합니다. 로컬 Compose는 development target, ECR은 production target을 사용합니다.

FROM base AS development-dependencies
FROM base AS production-dependencies
FROM production-dependencies AS production
CMD ["gunicorn", ..., "config.asgi:application"]

운영 이미지는 비root app 사용자로 실행됩니다. 앱 코드와 두 Compose 파일도 이미지 안에 들어가 EC2에서 같은 버전으로 꺼냅니다.

Dockerfile 원본
Docker Compose · runtime로컬과 EC2의 실행 차이

docker-compose.yml은 앱·PostgreSQL·소스 마운트를 구성합니다. 운영 override는 DB 컨테이너, 호스트 포트, 소스 마운트를 제거하고 외부 DB URL을 사용합니다.

127.0.0.1:${TRACEBACK_POSTGRES_PORT:-15432}:5432
db: !reset null
ports: !reset []
volumes: !reset []

호스트의 Django는 localhost:15432, Compose 안의 앱은 db:5432로 로컬 DB에 접속합니다. EC2의 앱은 서버 .env의 외부 DB를 사용합니다. 운영 healthcheck는 allauth config HTTP 요청으로 DB 경로까지 확인합니다.

docker-compose.yml · docker-compose_prod.yml · 로컬 실행 명령
Configuration · outside repositoryGitHub 변수와 서버 비밀값

.env.dev.git와 .env.prod.git은 GitHub Environment 변수의 예시 목록입니다. workflow가 파일을 읽지는 않습니다. EC2의 실제 Django 비밀값은 각 서버의 /opt/traceback/.env에 둡니다.

GitHub: AWS_REGION · AWS_DEPLOY_ROLE_ARN · ECR_REPOSITORY · INSTANCE_ID
EC2: TRACEBACK_DATABASE_URL · DJANGO_SECRET_KEY · Kakao · SES

현재 GitHub development Environment에는 필수 변수 4개가 없어 원격 개발 배포가 시작되지 못했습니다. 로컬/CI 품질 검사는 이 변수 없이도 실행됩니다. 설정 절차는 배포 문서에 있습니다.
