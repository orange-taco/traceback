가입 메일은 누가 만들고,
어떻게 받은 편지함까지 갈까?

allauth는 확인·재설정 메일이 필요한 시점과 링크를 정합니다. Django mailer는 메시지를 발송 서비스에 넘깁니다. SMTP는 그때 쓸 수 있는 전송 규약이고, Amazon SES는 실제 메일 발송 서비스입니다. 네 이름은 같은 역할을 가리키지 않습니다.

메일 전송 성공과 이메일 검증 완료는 다릅니다. 사용자가 링크를 열고 확인 요청이 서버에 반영되어야 EmailAddress.verified가 바뀝니다.

먼저 용어를 구분

SMTP는 서비스 이름이 아니라 전송 방법입니다

SMTP · Simple Mail Transfer Protocol

메일을 보낼 때 클라이언트가 메일 서버와 대화하는 규약입니다. host, 포트, 인증 정보와 암호화 방식이 필요합니다. 메일을 받는 사용자의 IMAP/POP 접속과는 역할이 다릅니다.

SES · Amazon Simple Email Service

AWS의 메일 발송 서비스입니다. SMTP 인터페이스와 HTTPS API를 제공합니다. SES를 선택했다고 반드시 SMTP를 써야 하는 것은 아닙니다. 발신 주소/도메인 확인과 계정의 sandbox 상태를 별도로 관리합니다.

587의 STARTTLS와 465의 TLS는 어떻게 다른가요?

587에서는 SMTP 연결 뒤 STARTTLS 명령으로 TLS로 전환합니다. 465는 연결 시작부터 TLS를 사용합니다. 둘 다 암호화된 메일 전송 경로가 될 수 있습니다. TRACEBACK 설정은 EMAIL_PORT=587과 EMAIL_USE_TLS=true를 사용합니다. AWS는 EC2의 25번 포트 발송을 기본적으로 제한하므로 587 선택에도 실용적인 이유가 있습니다. AWS SES 연결 방식

DECISION 1 · 발송 경로

테스트, SMTP, API 중 어떤 경로를 쓸까?

콘솔 / 메모리 mailer

실제 메일을 보내지 않고 출력하거나 테스트에서 메시지를 수집합니다. 빠르고 무료로 흐름을 확인하지만 수신자·도메인·전달 문제는 검증하지 못합니다.

TRACEBACK 로컬·테스트

SES SMTP · 현재 AWS 선택

Django의 표준 SMTP mailer에 SES endpoint와 SMTP 자격 증명을 넣습니다. 구현 연결이 단순합니다. 서버 outbound 587, 발신 identity, sandbox 상태와 SMTP 비밀값을 관리해야 합니다.

AWS dev/prod 설계

SES HTTPS API 또는 다른 메일 서비스

SDK/API는 IAM role 또는 서비스 API 키와 공급자 기능을 활용할 수 있습니다. 메일 백엔드 어댑터와 오류·재시도 정책을 별도로 설계해야 합니다. 향후 대량 발송·이벤트 처리 요구가 생기면 비교합니다.

대안

TRACEBACK 이유: 초기 인증 메일 규모에서 기존 Django SMTP mailer와 같은 AWS 계정의 SES를 연결하는 경로가 단순합니다. SMTP 비밀번호는 AWS 콘솔 로그인 암호나 GitHub OIDC 자격과 다릅니다. AWS SES SMTP 문서

DECISION 2 · 언제 보낼까?

요청 중 발송 vs 큐에서 비동기 발송

요청 처리 중 발송 · 현재 구조

별도 작업자·큐가 없어 설정이 적습니다. 대신 SMTP 지연이나 오류가 가입·재전송 요청에 영향을 줄 수 있습니다. Django mailer의 SMTP timeout은 현재 10초입니다.

작업 큐로 발송 · 확장 선택지

요청 응답과 발송을 분리하고 재시도·속도 제한을 운영할 수 있습니다. 큐, 작업자, 중복 발송 방지와 관측 체계가 필요합니다. 현재 문서의 확정 설계는 아니며 필요성이 생길 때 결정합니다.

메일 전송 실패는 어떻게 확인하나요?

로컬 콘솔 출력은 실제 전달 성공을 증명하지 않습니다. AWS에서는 앱 오류, SES 발송 결과와 발신 identity 상태를 확인하고 실제 수신함에서 링크를 눌러야 합니다. SMTP가 메시지를 받아도 최종 수신함 도착은 별도 문제입니다. production 전에는 재전송, 반송·스팸, 링크 만료를 브라우저에서 검증합니다.

TRACEBACK · 하나의 확인 메일 경로

이메일 가입은 어디로 돌아오나요?

1
브라우저가 allauth Headless로 가입POST /_allauth/browser/v1/auth/signup. 이메일 인증은 필수입니다.
2
allauth → Django mailer로컬은 terminal console, 테스트는 memory, AWS 설정은 SES SMTP를 선택합니다.
3
SES SMTP 587 → 수신자AWS에서는 검증된 발신 identity·리전별 SMTP 자격·outbound 연결과 sandbox 정책이 맞아야 합니다.
4

5
EmailAddress.verified 확인서버가 인증 상태를 저장합니다. 링크 발송만으로 verified가 되는 것은 아닙니다.

기본 mailer · AWS용 SMTP

MAILERS는 Django 6.1의 실제 설정입니다. 서버의 .env에서 host·port·credentials·STARTTLS를 읽습니다. EMAIL_BACKEND만 설정해도 이 정의를 덮어쓰지는 않습니다.

정확한 발췌 · config/settings/base.py 101–114행

101 │ DEFAULT_FROM_EMAIL = os.getenv("DEFAULT_FROM_EMAIL", "no-reply@localhost")
102 │ MAILERS = {
103 │     "default": {
104 │         "BACKEND": "django.core.mail.backends.smtp.EmailBackend",
105 │         "OPTIONS": {
106 │             "host": os.getenv("EMAIL_HOST", "localhost"),
107 │             "port": int(os.getenv("EMAIL_PORT", "25")),
108 │             "username": os.getenv("EMAIL_HOST_USER", ""),
109 │             "password": os.getenv("EMAIL_HOST_PASSWORD", ""),
110 │             "use_tls": os.getenv("EMAIL_USE_TLS", "false").lower() == "true",

113 │     }
114 │ }

base의 SMTP 설정을 환경별 settings 파일이 덮어씁니다. 로컬은 메일 본문을 콘솔에서 보고, 테스트는 실제 네트워크 대신 메모리에서 검사합니다.

AWS에서 실제 연결할 때

DNS, SES, EC2 설정의 역할을 분리합니다

발신 identity와 DNS

SES 서울 리전에서 발신 이메일 또는 도메인을 확인합니다. 도메인 identity라면 SES가 안내한 DKIM DNS 레코드를 Route 53에 게시하고 상태를 확인합니다. 이 DNS 레코드는 API의 A 레코드와 목적이 다릅니다. AWS identity 확인

Sandbox와 수신 대상

SES sandbox에서는 검증된 주소·도메인 또는 mailbox simulator에만 보낼 수 있습니다. 임의 사용자에게 보내려면 해당 리전의 production access가 필요합니다. 현재 계정의 승인 여부는 콘솔 재확인 전에는 완료로 표시하지 않습니다. AWS sandbox 설명

EC2 런타임 비밀값

/opt/traceback/.env에 DEFAULT_FROM_EMAIL, EMAIL_HOST=email-smtp.ap-northeast-2.amazonaws.com, EMAIL_PORT=587, 리전별 SMTP 사용자·암호, EMAIL_USE_TLS=true를 채웁니다. EC2 outbound 587도 검증합니다. Vercel에는 이 비밀값을 넣지 않습니다.

실제 브라우저 검증

가입 → 메일 수신 → 링크 열기 → 인증 API → 로그인까지 확인합니다. 비밀번호 재설정·재전송도 시험합니다. SMTP 설정만 저장하거나 CI가 통과해도 사용자 수신은 검증되지 않습니다.

SES SMTP 자격 증명은 EC2 IAM Role과 같은가요?

아닙니다. 현재 선택한 SMTP 경로는 SES 전용 SMTP username/password를 Django가 읽습니다. EC2 IAM Role은 SSM·ECR pull에 쓰고, SES API 방식을 선택한다면 그때 필요한 SES API 권한을 별도로 설계합니다. SMTP 자격은 AWS 계정 로그인 암호나 일반 AWS access key와도 구별합니다. AWS SMTP 자격 설명
