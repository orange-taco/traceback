EC2에는 어떻게 접속할까?

큰 그림이 먼저 필요하면 TRACEBACK System Guide의 전체 흐름을 보세요. 여기서는 네트워크 접속 방식과 AWS 권한을 분리한 뒤 SSH와 SSM을 비교하고, 실제 명령 및 현재 선택을 설명합니다.

여기서 접속하려는 대상은 AWS에 있는 원격 EC2 컴퓨터입니다. SSH는 내 Mac/PC가 그 EC2의 SSH 프로그램(보통 22번 포트)에 새 연결을 엽니다. SSM Session Manager는 내 Mac/PC와 EC2 안의 Agent가 AWS 세션 서비스를 통해 입력과 결과를 주고받습니다. 아래에서 먼저 “누가 누구에게” 연결하는지부터 설명합니다.

누가 누구에게 연결하는지부터 정합니다

이 문서에서 “내 컴퓨터”는 명령을 입력하는 사용자의 Mac/PC, “접속 대상 서버”는 AWS에서 실행 중인 원격 EC2 인스턴스를 뜻합니다. “서버”는 특정 제품명이 아니라 요청을 받는 역할입니다. 내 Mac에서 웹 개발 서버를 켜고 브라우저가 localhost로 접속하면 그때는 내 Mac이 서버 역할을 합니다. 아래 SSH·SSM 설명의 대상은 그 로컬 서버가 아니라 원격 EC2입니다.

클라이언트 · 서버
연결을 요청하는 쪽과 그 요청을 받는 쪽입니다. SSH 예시에서는 내 Mac의 ssh 프로그램이 클라이언트, 원격 EC2의 sshd 프로그램이 서버입니다. 같은 컴퓨터도 다른 상황에서는 서버가 될 수 있습니다.
IP 주소 · 도메인 · localhost
IP는 통신할 컴퓨터의 숫자 주소, 도메인은 그 주소를 찾기 위한 이름입니다. localhost는 지금 명령을 실행하는 바로 그 컴퓨터 자신을 가리킵니다. 내 Mac에서의 localhost와 EC2 안에서의 localhost는 서로 다릅니다.
TCP · 포트
TCP는 두 컴퓨터의 프로그램이 연결을 맺어 데이터를 주고받는 방식입니다. IP가 컴퓨터를 가리킨다면 포트 번호는 그 컴퓨터 안에서 받을 프로그램을 고릅니다. EC2_IP:22는 EC2의 22번 포트에서 듣는 SSH 프로그램을 뜻합니다.
HTTP · HTTPS
HTTP는 브라우저가 웹페이지나 API를 요청하고 응답받을 때 사용하는 규칙입니다. HTTPS는 그 HTTP 통신을 TLS(전송 내용을 암호화하는 기술)로 보호합니다. 보통 목적지 포트는 HTTP 80, HTTPS 443입니다. SSH는 웹페이지 요청이 아니라 원격 명령을 위한 다른 규칙이고 보통 목적지 포트 22를 씁니다.
SSH · 셸
SSH(Secure Shell)는 다른 컴퓨터의 셸에 암호화해 접속하는 규칙입니다. 셸은 ls, pwd 같은 명령을 실행하는 프로그램입니다. 내 Mac 터미널에 명령을 쓰면 Mac의 셸에서 실행되고, EC2 접속 뒤에는 EC2의 셸에서 실행됩니다.
터미널 · CLI
터미널은 명령을 입력하고 결과를 보는 화면입니다. CLI(Command Line Interface)는 그 화면에서 ssh, aws처럼 글자 명령으로 프로그램을 조작하는 방식입니다.
공개 키 · 개인 키
SSH 키 인증 예시에서 공개 키는 접속 대상인 원격 EC2의 Linux 사용자 계정(예: ec2-user)의 ~/.ssh/authorized_keys에 등록합니다. 개인 키는 접속을 시작하는 내 Mac/PC에만 보관합니다. Mac의 SSH 클라이언트가 개인 키를 사용해 자신을 증명하고, EC2의 SSH 서버가 등록된 공개 키로 검사합니다. SSM Session Manager 셸 접속에는 이 SSH 키 쌍이 필요하지 않습니다.

SSH와 HTTPS는 같은 접속인가요?

둘 다 TCP 연결을 사용할 수 있지만 목적과 대화 규칙이 다릅니다. 내 Mac의 브라우저가 사이트를 열면 웹 서버에 HTTPS 요청(보통 443)을 보냅니다. 내 Mac의 터미널에서 ssh ec2-user@EC2_IP를 실행하면 EC2의 SSH 서버에 셸 접속(보통 22)을 요청합니다. SSM Agent가 AWS에 HTTPS 443으로 나가는 것은 SSM 서비스와 통신하기 위해서이며, 브라우저가 TRACEBACK 웹사이트를 여는 것과는 다른 연결입니다.

인바운드·아웃바운드는 누구 기준인가요?

항상 규칙을 붙인 컴퓨터 기준입니다. 내 Mac이 EC2의 SSH 22번으로 새 연결을 열면 EC2에는 인바운드입니다. 반대로 EC2의 SSM Agent가 AWS SSM 서비스의 443번으로 새 연결을 열면 EC2에는 아웃바운드입니다. 이 문서에서 “인바운드 22”와 “아웃바운드 443”은 접속 대상 EC2의 보안 그룹(AWS가 EC2에 붙이는 방화벽 규칙)을 기준으로 말합니다.

EC2에 인바운드 443 규칙이 없어도 SSM의 응답은 왜 돌아오나요?

EC2가 AWS SSM 서비스로 먼저 연결을 열면, EC2의 보안 그룹은 그 연결을 기억합니다. AWS가 같은 연결로 돌려보내는 데이터는 “AWS가 EC2에 새로운 연결을 여는 것”과 다릅니다. AWS 보안 그룹은 이렇게 연결 상태를 추적하므로 허용된 아웃바운드 요청의 응답은 별도의 인바운드 규칙 없이 돌아올 수 있습니다. 반대로 AWS가 처음부터 EC2에 새 연결을 열려면 EC2의 인바운드 허용이 필요합니다. 이 성질을 상태 저장(stateful)이라고 합니다. 이 설명은 EC2 보안 그룹 기준이며, 별도로 설정한 네트워크 ACL이나 OS 방화벽은 따로 점검해야 합니다. AWS: 보안 그룹의 상태 저장 동작

TRACEBACK 개발 EC2에 대입하면: 현재 개발 EC2의 보안 그룹에는 인바운드 TCP 22 규칙이 없습니다. 따라서 내 Mac에서 ssh ec2-user@EC2_공인IP로 새 SSH 연결을 열 수 없습니다. EC2의 SSM Agent는 AWS SSM 서비스로 나가는 HTTPS 443 경로를 사용합니다. 개인 키 파일을 만드는 것만으로 닫힌 22번 경로가 열리지는 않습니다.

이제 같은 연결을 AWS 제품과 권한으로 번역합니다. 사람의 권한(②)과 EC2 Agent의 권한(④)은 서로 다른 신원입니다.

AWS의 장소 → 길 → 출입 규칙 → 사용 권한

접속 대상은 어디에 있고, 누가 문을 열어 주나요?

먼저 컴퓨터의 위치를 그린 다음 네트워크 길과 AWS 사용 권한을 각각 겹쳐 봅니다. AWS에서 EC2는 가상 컴퓨터를 만드는 서비스 이름이고, EC2 인스턴스는 그 서비스로 실행한 컴퓨터 한 대입니다. 다음 그림의 가장 안쪽 컴퓨터가 우리가 접속할 대상입니다.

AWS 계정 · 리소스를 소유하고 권한을 관리한 계정에 여러 VPC와 EC2 인스턴스를 만들 수 있음
① VPC · 내 AWS 가상 네트워크의 큰 경계서브넷과 라우팅을 담는 네트워크. 서로 다른 VPC는 자동으로 이어지지 않음
② 서브넷 · VPC 안의 한 IP 주소 구간EC2를 어느 구간에 놓을지 결정. 한 서브넷은 한 가용 영역에 속함
③ EC2 인스턴스 · 실제 접속할 가상 컴퓨터서브넷의 주소를 가진 네트워크 인터페이스(ENI)를 통해 통신
④ 라우팅 테이블 · 어디로 보낼까?

서브넷에 연결된 목적지별 길 안내입니다. 같은 VPC 안 주소는 local, 인터넷 목적지는 인터넷 게이트웨이(IGW)로 보내는 식입니다. 명시적 연결이 없으면 VPC의 기본(main) 테이블을 씁니다.

⑤ 보안 그룹 · 이 연결을 허용할까?

EC2의 네트워크 인터페이스에 붙는 인바운드·아웃바운드 허용 규칙입니다. 서브넷의 하위 공간이나 라우팅 테이블의 일부가 아닙니다. 길이 있어도 해당 연결이 허용되지 않으면 통과하지 못합니다.

⑥ IAM · 누가 AWS 작업을 해도 될까?

사람이 ssm:StartSession을 요청할 권한, EC2 Agent가 AWS와 통신할 권한을 정합니다. 네트워크가 열려 있어도 AWS API 권한이 없으면 SSM 세션을 시작할 수 없습니다.

그림 읽는 법: ①→②→③은 포함·배치 관계입니다. ④·⑤·⑥은 그 안에 또 들어가는 층이 아니라, ③의 통신에 각각 적용되는 길·네트워크 허용·AWS 작업 허용입니다. AWS가 제공하는 기본 VPC를 사용하면 ①·②·④ 일부가 미리 만들어져 있을 수 있으므로, 매번 손으로 새 VPC부터 만드는 절차라는 뜻은 아닙니다. AWS VPC 구조 · AWS 서브넷과 라우팅 테이블

VPC가 먼저인가요, 서브넷이 먼저인가요?

구조상 VPC가 부모입니다. 서브넷은 반드시 어떤 VPC에 속하며, EC2를 시작할 때 그 인스턴스의 네트워크 인터페이스를 서브넷에 둡니다. 직접 새 네트워크를 설계한다면 VPC → 서브넷/라우팅 → EC2 순서로 준비합니다. 기존 기본 VPC를 사용한다면 그 안의 서브넷과 경로를 선택·확인합니다.

‘공개 서브넷’이면 누구나 EC2에 접속하나요?

아닙니다. 인터넷 목적지 경로가 IGW로 향하는 서브넷을 보통 공개 서브넷이라고 부릅니다. 인터넷에서 EC2의 공개 IPv4/EIP로 직접 접속하려면 그 주소, 서브넷 경로, EC2 보안 그룹 인바운드 허용, 수신 프로그램도 맞아야 합니다. SSM 셸은 EC2의 22번 인바운드 대신 Agent의 443 아웃바운드 경로를 씁니다. AWS 공개 서브넷 경로

VPC와 서브넷을 왜 둘로 나누나요? 리전·가용 영역은 또 무엇인가요?

리전은 AWS가 서비스를 운영하는 지리적 지역이고, 가용 영역(AZ)은 리전 안에서 장애 영역을 나눈 장소입니다. VPC는 한 리전의 네트워크 주소 공간과 연결 경계를 정합니다. 그 VPC를 여러 서브넷으로 나누어, 각 서브넷을 한 가용 영역에 배치합니다. 예를 들어 웹 서버가 있는 서브넷에는 인터넷 경로를 주고 DB 서브넷에는 직접 인터넷 경로를 주지 않을 수 있습니다. 이 구분 덕분에 같은 VPC 안에서도 자원을 어느 주소 구간·장애 영역·경로에 둘지 선택할 수 있습니다. 서브넷 이름만 ‘private’으로 붙인다고 비공개가 되는 것은 아니고 실제 라우팅과 공개 주소, 접근 규칙을 함께 봐야 합니다.

사람과 EC2는 서로 다른 AWS 권한으로 Session Manager에서 만납니다

여기서 SSM은 AWS Systems Manager 서비스의 약칭, Session Manager는 SSM 안에서 원격 셸을 여는 기능입니다. 세션은 내 터미널과 원격 EC2 셸 사이에서 한 번 열려 종료할 때까지 이어지는 대화입니다. SSM은 SSH의 다른 이름이 아닙니다.

사람 · 내 Mac/PC에서 요청

  1. IAM Identity Center가 사람의 로그인과 계정 접근을 관리. SSO는 허용된 여러 자원에 한 로그인으로 들어가는 방식입니다.
  2. 관리자가 사용자/그룹 + AWS 계정 + Permission set(권한 묶음)을 할당합니다. Identity Center가 해당 계정에 IAM 역할을 마련합니다.
  3. 내 컴퓨터의 AWS CLI 프로필은 사용할 포털·계정·권한 묶음을 가리키는 설정입니다. aws sso login 뒤 CLI가 임시 자격 증명을 얻습니다.
  4. CLI가 대상 EC2의 ssm:StartSession을 요청합니다. 로그인만 했고 이 권한이 없으면 거절됩니다.

EC2 인스턴스 · AWS와 통신

  1. EC2 안에서 SSM Agent 프로그램이 실행됩니다.
  2. EC2에 연결된 인스턴스 프로파일이 Agent에게 IAM 역할의 임시 자격 증명을 제공합니다. 역할에는 SSM 관리 대상 통신 권한이 필요합니다.
  3. Agent가 EC2 보안 그룹 아웃바운드와 서브넷의 경로를 이용해 AWS SSM 서비스의 HTTPS 443으로 연결합니다.
  4. Session Manager가 두 쪽을 이어 주면 EC2 안에서 Linux 셸이 열립니다. ssm-user는 이 Linux 계정이며, Identity Center 사용자나 IAM 역할과 다릅니다.
두 경로의 만남: 사람의 권한은 “이 EC2에 세션을 요청해도 되는가?”, EC2 역할은 “이 Agent가 SSM에 등록·통신해도 되는가?”를 답합니다. 둘 다 맞아야 합니다. Session Manager plugin은 내 컴퓨터의 터미널 입출력을 세션에 연결합니다. AWS Identity Center 임시 자격 증명 · AWS EC2 역할
IAM 정책, 역할, Permission set은 서로 어떻게 다른가요?

정책(Policy)은 “어떤 AWS API 작업을 어떤 대상에 허용할지” 적은 규칙입니다. 역할(Role)은 그 규칙을 붙이고 조건에 맞는 주체가 잠시 맡는 AWS 신원입니다. Permission set은 Identity Center 관리자가 사람에게 AWS 계정 접근을 할당할 때 고르는 권한 묶음이며, Identity Center가 대상 계정에 대응하는 IAM 역할을 마련합니다. EC2의 인스턴스 프로파일은 EC2에 별도 IAM 역할을 연결합니다. 따라서 사람의 Permission set에 SSM 권한을 넣어도 EC2 Agent 역할의 권한이 자동으로 생기지 않고, 반대도 마찬가지입니다. AWS Permission set

Identity Center가 왜 필요한가요? IAM 사용자 키로도 되나요?

내 컴퓨터의 CLI가 AWS에 “누가 세션을 시작하는지” 증명해야 하기 때문입니다. Identity Center는 사람의 브라우저 로그인과 계정 권한 할당을 관리하고 CLI에 만료되는 임시 자격 증명을 제공합니다. IAM 사용자의 장기 Access Key 등 다른 인증 수단도 가능하지만 키를 보관·교체해야 합니다. Identity Center를 쓰더라도 권한 묶음에 대상 EC2의 세션 권한이 없으면 접속할 수 없습니다.

라우팅 테이블, 보안 그룹, IAM 중 무엇부터 확인하나요?

서로 대체하지 않는 세 질문으로 나눕니다. 라우팅 테이블은 EC2가 AWS SSM 서비스까지 갈 길을 찾는지, EC2 보안 그룹은 그 아웃바운드 HTTPS 연결을 허용하는지, IAM은 사람의 세션 요청과 Agent의 서비스 통신을 허용하는지 검사합니다. SSM이 연결되지 않으면 모두 확인합니다. SSH를 택한 경우에는 내 PC에서 EC2까지의 경로와 EC2의 인바운드 22 허용 여부가 추가로 중요합니다.

SSM은 어떤 원리로 동작하나요? SSH처럼 22번 포트로 들어가나요?

로컬 AWS CLI가 StartSession API를 요청합니다. Session Manager는 사용자 신원과 IAM 권한을 검사하고 EC2의 SSM Agent에 세션 시작을 알립니다. Agent는 AWS의 Systems Manager 통신 경로에 HTTPS/TLS로 아웃바운드 연결합니다. 로컬 plugin과 Agent가 세션 채널로 입력·출력을 주고받으므로 일반 셸 접속에 EC2 인바운드 22번 포트가 필요하지 않습니다. EC2는 AWS 서비스에 닿을 수 있어야 하며 인터넷 경로나 적절한 VPC 엔드포인트를 사용합니다. AWS: Session Manager 작동 방식 · AWS: 네트워크 전제 조건

어떤 권한으로 접속하나요? 내 AWS 로그인과 EC2 역할은 같은 것인가요?

두 신원이 필요합니다. 사람의 AWS 신원에는 대상 EC2에 ssm:StartSession을 요청할 IAM 권한이 있어야 합니다. 로그인은 Identity Center나 다른 임시 자격 증명으로 구성할 수 있습니다. EC2의 신원은 Agent가 Systems Manager에 통신할 권한을 제공합니다. EC2 인스턴스 프로파일에 AmazonSSMManagedInstanceCore를 붙이는 것이 한 방법입니다. 이는 사람에게 세션 시작 권한을 주는 것과 별개입니다. 세션 안의 Linux 계정 ssm-user도 AWS 로그인 사용자와 다른 OS 계정입니다. AWS: 사용자 세션 접근 제어 · AWS: 인스턴스 권한

SSM과 SSH는 언제 각각 쓰나요?

둘 다 서버 셸에 접근할 수 있습니다. SSH는 서버의 SSH 서비스까지 도달해야 하고 키·사용자·22번 인바운드 규칙을 관리합니다. Session Manager는 AWS 신원과 Agent·아웃바운드 경로를 준비하며 세션 권한을 IAM으로 제어합니다. 조직 정책과 네트워크 구조에 따라 SSH, SSM 또는 둘 다 사용할 수 있습니다. TRACEBACK은 개발 EC2의 22번 포트를 열지 않는 SSM 경로를 선택했습니다.

두 경로를 비교

SSH와 SSM은 연결을 시작하는 쪽이 다릅니다

필요 조건: EC2 주소 도달 가능, 인바운드 TCP 22 허용, 서버 SSH 서비스, 올바른 사용자명과 개인 키. 22번을 인터넷 전체에 열면 공격 시도가 계속 들어올 수 있으므로 보통 출발지 IP를 제한합니다.

핵심: 22번 SSH 연결을 SSM이 대신 전달하는 것이 아니라, Session Manager가 별도 세션 채널을 제공합니다. Agent가 먼저 바깥으로 나가므로 서버로 들어오는 신규 22번 연결이 필요 없습니다. Agent의 HTTPS 아웃바운드 경로(또는 SSM VPC Endpoint)가 있어야 합니다.

참고: SSM은 별도 기능으로 SSH 트래픽을 Session Manager 터널 안에 넣을 수도 있습니다. 이 안내서의 start-session은 SSH 터널이 아니라 일반 셸 세션입니다.

왜 1~7을 모든 AWS 사용자가 그대로 따라 하는 표준 절차라고 볼 수 없나요?

SSM Session Manager의 필수 조건과 접속 명령은 공통이지만, traceback-dev 프로필 이름, Identity Center 포털, 계정·인스턴스 ID, 셸 함수는 이 프로젝트와 컴퓨터의 선택입니다. 다른 조직은 다른 임시 역할이나 콘솔을 사용할 수 있습니다. CLI 방식의 표준 명령은 aws ssm start-session --target <instance-id>이며, aws ssm traceback-dev는 AWS가 제공하는 하위 명령이 아닙니다. AWS: 세션 시작 방식

1

AWS IAM Identity Center 사용자 준비

일반적으로 계정 관리자가 사용자를 만들고 AWS 계정과 필요한 Permission Set을 할당합니다. 사용자는 초대받은 뒤 암호와 MFA를 설정합니다. 이 사람의 로그인 권한은 EC2에 붙는 IAM Role과 별개입니다.

현재 TRACEBACK은 사용자 oscar, access portal https://d-9b675ce989.awsapps.com/start, 서울 Identity Center를 사용합니다. 사용자와 MFA 설정은 완료됐습니다. 실제 운영에서는 업무에 필요한 범위만 허용하는 Permission Set을 사용합니다.

2

CLI에 구분 가능한 프로필 만들기

프로필은 내 컴퓨터에서 AWS 접속 대상을 구분하는 이름입니다. 여러 계정이나 환경을 쓸 때는 모호한 default보다 목적이 드러나는 이름이 실수를 줄여줍니다.

AWS CLI 실행 명령 · 저장소 소스 파일이 아닙니다
aws configure sso --profile traceback-dev

터미널이 물어보면 다음처럼 입력합니다.

  • SSO session name: traceback
  • SSO start URL: https://d-9b675ce989.awsapps.com/start
  • SSO region: ap-northeast-2
  • SSO registration scopes: 기본값 sso:account:access 그대로 Enter

브라우저가 열리면 Identity Center 사용자를 선택하고, 관리자에게 할당받은 AWS 계정과 Permission Set을 고릅니다. 현재 TRACEBACK 계정 ID는 968579693658입니다. 뒤이어 CLI가 물어보는 값은 아래와 같습니다.

CLI default client Region → ap-northeast-2 (EC2가 있는 서울)
CLI default output format → json
CLI profile name → traceback-dev

세션 이름은 로그인 세션 설정의 이름이고, 프로필 이름은 명령에서 --profile 뒤에 적는 로컬 별칭입니다. 둘 다 같은 문자열이어도 서로 다른 항목입니다. CLI가 만든 프로필 메타데이터는 보통 ~/.aws/config에 기록됩니다. 실제 임시 SSO 토큰은 만료 가능한 캐시에 보관되며, Access Key를 이 문서에 복사해 적는 방식이 아닙니다.

3

브라우저 SSO 로그인

AWS CLI 실행 명령 · 저장소 소스 파일이 아닙니다
aws sso login --profile traceback-dev

브라우저에서 IAM Identity Center 로그인을 완료합니다. AWS CLI는 임시 자격 증명을 로컬 SSO cache에 보관하고 만료되면 다시 로그인합니다. 장기 Access Key를 직접 복사해 넣는 방식과 다릅니다.

4

목표 AWS 계정이 맞는지 확인

AWS CLI 실행 명령 · 저장소 소스 파일이 아닙니다
aws sts get-caller-identity \
  --profile traceback-dev \
  --query Account \
  --output text

출력이 현재 접속하려는 계정 ID 968579693658인지 확인합니다. 다른 계정 번호가 나오면 대상이 아닌 계정일 수 있으므로 SSM 접속 명령을 실행하지 말고 프로필 선택을 확인합니다.

이 검사는 현재 CLI가 어떤 계정의 어떤 권한으로 AWS 명령을 실행하는지 알려줍니다.

5

Session Manager plugin 확인

AWS CLI가 SSM 세션을 터미널에 연결할 때 로컬 Session Manager plugin을 사용합니다. AWS CLI와 별도 구성요소이므로 운영체제에 맞는 AWS 설치 안내로 설치한 뒤 확인합니다.

로컬 plugin 확인 명령 · 저장소 소스 파일이 아닙니다
command -v session-manager-plugin
session-manager-plugin

현재 Mac에서는 plugin이 ~/.local/bin에 있어 이 디렉터리를 PATH에 추가했습니다. 실행 파일을 못 찾을 때만 export PATH="$HOME/.local/bin:$PATH"를 ~/.zshrc에 추가합니다. 이 경로는 현재 컴퓨터의 설치 방식이며 다른 컴퓨터에서는 달라질 수 있습니다.

6

개발 인스턴스에 세션 시작

AWS CLI의 표준 세션 명령 · 저장소 소스 파일이 아닙니다
aws ssm start-session \
  --target i-051f85a1ac4e64a2c \
  --region ap-northeast-2 \
  --profile traceback-dev

성공하면 원격 Linux 셸 프롬프트가 나타납니다. 작업을 끝내면 exit를 입력해 세션을 닫습니다. 이 명령은 EC2나 RDS를 만들거나 시작/중지하지 않고, 실행 중인 EC2에 셸 연결만 엽니다.

현재는 셸 함수로 aws ssm traceback-dev를 입력하면 위 긴 명령을 실행합니다. 짧은 명령은 AWS CLI 기본 명령이 아니라 내 컴퓨터에 추가한 편의 설정입니다.

SSM 접속은 됐는데 cd /opt/traceback이 Permission denied인 이유는?

SSM 접속 권한과 Linux 파일 권한은 다른 단계입니다. SSM은 셸을 열어 주지만 모든 폴더의 소유권을 주지는 않습니다. 현재 셸은 ssm-user이고, TRACEBACK의 실행 폴더는 비밀 환경 파일을 보호하려고 root 전용으로 준비됐습니다. /opt 목록을 볼 수 있어도 그 안의 traceback 디렉터리에 들어가려면 해당 디렉터리의 실행(x) 권한이 필요합니다. ec2-user와 ssm-user도 서로 다른 Linux 사용자이며 홈 디렉터리가 자동 동기화되지 않습니다.

EC2 셸에서 확인하는 명령 · 저장소 소스 파일이 아닙니다
whoami
id
ls -ld /opt /opt/traceback
namei -l /opt/traceback

관리 권한이 부여된 경우에만 sudo -i로 root 셸을 연 뒤 cd /opt/traceback으로 이동하고, 마치면 exit로 돌아옵니다. cd는 셸 내부 명령이므로 sudo cd /opt/traceback은 해결 방법이 아닙니다. 폴더를 모두에게 공개하도록 chmod 777하지 않습니다.

일반적인 운영 선택지: root 전용 폴더는 비밀값 보호가 단순하지만 관리자는 sudo가 필요합니다. 전용 배포 사용자·그룹을 두면 일상 작업을 분리할 수 있지만 소유권·그룹·파일 권한을 함께 설계해야 합니다. TRACEBACK은 초기 한 대 서버에서 root 전용 폴더와 root 소유 .env를 택했습니다. 서버 환경 파일 위치와 배포 방식 비교

7

선택 사항 · TRACEBACK 로컬 단축 명령

AWS CLI 자체에는 aws ssm traceback-dev 명령이 없습니다. 현재는 ~/.zshrc의 셸 함수가 이 입력을 가로채, 자격 증명이 만료됐으면 SSO 로그인 후 긴 start-session 명령을 실행합니다. 나머지 aws ... 명령은 원래 CLI로 전달합니다.

로컬 ~/.zshrc 셸 함수 예시 · AWS CLI 기본 명령이나 저장소 소스 파일이 아닙니다
aws() {
  if [[ "$#" -eq 2 && "$1" == "ssm" && "$2" == "traceback-dev" ]]; then
    command aws sts get-caller-identity --profile traceback-dev >/dev/null 2>&1 || {
      command aws sso login --profile traceback-dev || return
    }
    command aws ssm start-session \
      --target i-051f85a1ac4e64a2c \
      --region ap-northeast-2 \
      --profile traceback-dev
  else
    command aws "$@"
  fi
}

편집 후 source ~/.zshrc로 현재 셸에 다시 읽힙니다. 이 함수에는 dev 인스턴스 ID가 직접 들어 있으므로 prod 대상에 그대로 쓰지 말고, 별도 프로필·대상을 확인해야 합니다.

각 이름의 뜻: --profile traceback-dev는 사람의 AWS 로그인 신원, --region ap-northeast-2는 명령 대상 리전, --target i-...는 접속할 EC2입니다. AWS 계정·리전·대상은 서로 다릅니다. 짧은 명령은 이 조합을 미리 실행하도록 만든 셸 편의 설정입니다.
세 가지 AWS 권한 경로를 구분: 로컬 터미널은 IAM Identity Center(SSO)로 로그인한 사람의 임시 권한으로 ssm:StartSession을 요청합니다. GitHub Actions는 OIDC로 GitHub 저장소·브랜치/Environment를 증명하고 배포용 IAM Role을 잠시 맡아 ECR push와 SSM 명령 전송을 합니다. EC2 안의 SSM Agent와 ECR pull은 인스턴스 프로파일에 연결된 EC2 IAM Role로 실행됩니다. 사람 로그인, 자동화 신원, 서버 신원은 서로 다른 역할입니다.

접속 절차를 TRACEBACK에 대입해 ①~⑤ 중 무엇이 준비됐는지 확인합니다.

확인된 TRACEBACK dev 값

현재 리소스 상태를 이 절차에 대입하면

접속 대상

EC2 traceback-development-app
Instance ID i-051f85a1ac4e64a2c
Region ap-northeast-2 (서울)

인스턴스 쪽 준비

SSM Agent Online 확인됨. traceback-development-ec2 인스턴스 프로파일에 AmazonSSMManagedInstanceCore가 연결됨.

네트워크 쪽 준비

보안 그룹 인바운드 TCP 80/443, TCP 22 규칙 없음. 기본 아웃바운드 전체 허용으로 Agent의 HTTPS 통신 경로가 있음.

로컬 컴퓨터 쪽 준비

AWS CLI v2, Session Manager plugin, Identity Center의 traceback-dev 프로필, aws ssm traceback-dev 함수가 준비됨. 현재 Permission Set은 AdministratorAccess입니다. SSM 접속에는 이처럼 넓은 계정 권한이 필요하지 않으므로 장기적으로 SSM 대상 범위를 제한한 Permission Set으로 분리하는 편이 최소 권한 원칙에 맞습니다.

비용: 이 EC2에 대한 기본 Session Manager 셸 연결은 별도 세션 요금이 없다. EC2 인스턴스·공인 IPv4 등 기존 실행 비용은 계속 발생할 수 있다. 선택형 로그 수집을 켜면 CloudWatch Logs나 S3 사용 요금이 추가될 수 있다.

상태 출처: 이 저장소의 AWS 배포 설정 문서와 작업 체크포인트. AWS 설정은 변경될 수 있으므로 접속 전 계정·인스턴스 상태를 다시 확인합니다.

여기부터는 기본 접속 절차의 대안 경로입니다. 먼저 EC2 Agent가 AWS에 나가는 ④의 네트워크 출구를 비교합니다.

VPC Endpoint가 필요한 경우

현재 dev EC2에는 새로 만들 필요가 없습니다

VPC Endpoint는 VPC 안의 EC2가 AWS 서비스의 private IP로 연결하도록 만들어 주는 네트워크 인터페이스입니다. SSM Endpoint를 만들어도 사용자 노트북이 EC2에 직접 연결되는 것은 아닙니다. EC2 안의 SSM Agent가 AWS Systems Manager로 나가는 경로가 바뀝니다.

지금 TRACEBACK dev

EC2는 public subnet과 public IP를 사용하고, 보안 그룹 outbound는 기본 허용이며 SSM Agent가 Online으로 확인된 상태입니다. 따라서 이미 SSM 통신 경로가 작동합니다. 접속을 위해 SSM VPC Endpoint를 추가 생성할 필요가 없습니다.

나중에 private subnet으로 옮긴다면

SSM Agent가 SSM 서비스의 HTTPS/443 endpoint로 나갈 길이 필요합니다. NAT Gateway를 통하거나, VPC 안에 SSM interface endpoint를 만듭니다. Interface endpoint는 서비스별·가용 영역별 시간 요금과 데이터 처리 요금이 있어 사용하지 않을 때도 켜져 있으면 비용이 생길 수 있습니다.

이름이 왜 endpoint인가요? AWS 서비스 쪽으로 향하는 private 진입 지점을 VPC 안에 만들어 주기 때문입니다. DNS가 SSM 서비스 이름을 그 endpoint network interface의 private IP로 해석하고, Agent는 그 주소로 outbound 연결을 엽니다. Endpoint가 인스턴스의 인바운드 22번 포트를 열거나 IAM 권한을 대신 주지는 않습니다.

SSM Agent는 ssm 및 ssmmessages 서비스 endpoint와 HTTPS/443으로 통신합니다. 오래된 Agent/구성에서는 ec2messages가 추가로 필요할 수 있습니다. 실제 구성 시점의 Agent 버전과 AWS Region 요구사항을 확인하세요.

이번에는 ①→⑤ 전체 접속 방식을 바꾸는 선택지입니다. Bastion은 SSH로 사설 서버에 접근할 때 중간에 두는 점프 서버이며 위 SSM 경로의 필수 구성요소가 아닙니다.

Bastion과 SSM

SSH 경로에 중간 서버가 필요할 때 Bastion을 둡니다

점프 서버 경로 · SSH 중심

내 컴퓨터 → Bastion → 사설 EC2. 첫 연결은 Bastion에, 두 번째 연결은 Bastion에서 사설 서버에 엽니다. 사설 EC2가 외부에서 직접 닿지 않을 때 중간 진입점 역할을 합니다.

Agent 경로 · SSM 중심

내 컴퓨터 → Session Manager ↔ 사설 EC2의 Agent. 사설 EC2 자체가 관리 대상이고 AWS 서비스로 나갈 경로가 있으면 Bastion을 거치지 않고 세션을 엽니다. TRACEBACK이 쓰는 접속 방식입니다.

혼합 경로 · SSM으로 Bastion에 진입

내 컴퓨터 → Session Manager ↔ Bastion의 Agent → 사설 대상. SSM은 Bastion 접속을 보호하고, Bastion은 그 다음 사설 대상에 접근합니다. AWS의 구성 예시가 있습니다.

Bastion이란?

일반 네트워크 용어로는 외부 사용자와 내부 서버 사이에 두는 점프용 서버입니다. 사용자는 먼저 Bastion에 접속하고, 거기서 사설망의 대상 서버로 다시 연결합니다. 보통 대상 EC2는 공인 인터넷에 직접 노출하지 않습니다.

우리의 현재 구조

개발 EC2가 SSM 관리 대상으로 등록되어 있으므로 각 환경 EC2에 직접 Session Manager로 접속하면 됩니다. 운영 EC2가 생겨도 권한을 dev/prod 인스턴스별로 제한해 각각 직접 접속할 수 있습니다. SSM은 Bastion을 통해서도 쓸 수 있지만, 현재 두 서버 접근만을 위해 중간 EC2를 추가하면 관리 대상과 비용이 늘어납니다.

나중에 사설 네트워크 내부의 여러 서버를 통제된 단일 진입점으로 관리해야 한다면 Bastion이나 SSM port forwarding을 별도 설계합니다. SSM을 쓰기 위해 Bastion을 만들 필요는 없습니다.

마지막으로 전체 지도 ①~⑤ 중 어디서 끊겼는지 역순으로 확인합니다. 에러가 난 위치에 따라 신원·권한·출구·Agent를 분리해 봅니다.

오류가 나면 확인할 곳

접속 문제는 네트워크와 권한을 분리해 찾습니다

다른 계정 번호 출력--profile traceback-dev를 빠뜨렸거나 프로필 선택이 잘못됐습니다. 계정 ID 968579693658를 확인하기 전에는 다음으로 진행하지 않습니다.
SSO 계정/역할이 목록에 없음IAM Identity Center에서 사용자에게 대상 AWS 계정과 SSM 권한이 있는 Permission Set을 할당했는지 확인합니다. CLI 옵션으로 우회할 수 있는 네트워크 문제가 아닙니다.
AccessDeniedException사용자 Permission Set에 ssm:StartSession과 대상 인스턴스 권한이 있는지 확인합니다. EC2 인스턴스 프로파일 권한과 사용자의 세션 권한은 별개입니다.
TargetNotConnectedEC2가 실행 중인지, SSM Agent가 Online인지, Agent의 IAM instance profile이 붙었는지, EC2가 SSM 서비스로 HTTPS/443 아웃바운드 통신할 수 있는지 점검합니다.
plugin을 찾을 수 없음설치 위치를 확인하고 필요하면 export PATH="$HOME/.local/bin:$PATH"를 실행합니다. 설치 위치는 OS와 설치 방법에 따라 달라질 수 있습니다.
SSH timeout예상된 결과입니다. 현재 보안 그룹에 인바운드 22가 없으므로 SSH 대신 Session Manager를 사용합니다.
RDS는 별도 연결입니다. EC2에 SSM 셸을 열었다고 내 컴퓨터가 RDS에 연결되는 것은 아닙니다. RDS는 private 상태이며 5432는 EC2 보안 그룹에서 오는 연결만 허용합니다. 데이터베이스에 접속하려면 먼저 EC2에서 실행하거나 SSM port forwarding을 별도로 설정해야 합니다.
