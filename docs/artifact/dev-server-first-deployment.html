현재 준비 상태

GitHub와 AWS의 배포 신뢰 경로(OIDC·IAM·ECR)는 준비됐습니다. 첫 배포 전에 EC2가 ECR 이미지를 pull할 권한과 서버 실행 환경을 갖추고, 런타임 설정과 TLS를 완료해야 합니다.

✓
AWS/GitHub 준비됨OIDC · IAM · ECR · GitHub Environment

현재 준비 상태: API 이름 api.dev-traceback.com과 Route 53 A 레코드, EIP 연결은 끝났습니다. 이제 EC2 앞단이 HTTPS를 처리하도록 TLS 인증서와 Nginx를 설정해야 합니다. DNS 이름이 준비됐다는 것만으로 TLS나 Django API가 동작하지는 않습니다.

로컬 Docker DB와 AWS RDS는 역할이 달라요

현재 프로젝트의 기본 구성은 로컬·CI·AWS 환경마다 분리된 PostgreSQL입니다. 앱 컨테이너를 쓴다고 dev/prod에서도 DB 컨테이너를 써야 하는 것은 아닙니다.

로컬 개발

Docker Compose PostgreSQL

개발자 Mac에서 앱을 빠르게 실행하고 테스트하는 개인 DB입니다. 네트워크 연결 없이 쓸 수 있고 데이터를 쉽게 초기화할 수 있습니다.

docker compose up -d db

현재 기본은 PostgreSQL 17, host port 15432. 로컬 데이터는 AWS dev RDS와 공유하지 않습니다.

AWS dev·prod

환경별 관리형 RDS

개발 EC2의 Django 컨테이너는 private dev RDS에, 나중에 prod EC2 앱은 별도 prod RDS에 연결합니다.

Compose overlay가 내부 db 컨테이너를 제거하고, 각각의 TRACEBACK_DATABASE_URL을 요구합니다.

EC2의 IAM 역할은 네트워크를 열어주지 않습니다. RDS security group의 5432 source와 앱 DB 계정·URL이 모두 맞아야 합니다.

GitHub CI

일회성 테스트 PostgreSQL

CI workflow가 테스트 job 동안 임시 PostgreSQL service를 띄웁니다. 이것은 로컬 DB도 RDS도 아니며, CI 완료 후 없어집니다.

세 DB는 같은 PostgreSQL major version을 쓰고 migration으로 schema를 맞추되, 데이터베이스 자체와 사용자 데이터는 공유하지 않습니다.

로컬 Djangohost-run 또는 app container
Local Docker DBCompose `db`, 개인 개발 데이터
AWS EC2 Docker appdev와 prod에서 동일한 앱 이미지
각 환경의 RDSdev DB와 prod DB는 별도 endpoint·계정·비밀값
경계로컬 DB → RDS로 자동 복사되지 않음. CI/CD도 앱 이미지만 배포
이게 일반적인 이유: 로컬 DB는 빠르고 안전한 작업 공간이고, RDS는 공유·백업·운영을 담당합니다. 스키마를 바꾸는 migration은 같은 앱 코드로 각 환경에 적용하지만, 로컬 테스트 데이터나 비밀번호는 dev/prod로 복사하지 않습니다.

요청과 배포는 두 개의 흐름입니다

브라우저 요청 경로와 코드 배포 경로는 별도로 이어집니다. RDS는 앱 내부망에 있고, S3는 현재 업로드 기능이 생길 때까지 비어 있어도 됩니다.

A · 사용자가 로그인하거나 API를 요청할 때

브라우저Vercel 도메인의 /_allauth, /accounts, 나중의 /api
Vercel SSR + rewrite브라우저 주소는 그대로 두고, 해당 경로만 개발 Django 원본에 전달
HTTPS · 개발 API 도메인DNS와 인증서가 유효한 주소. Vercel rewrite의 upstream
EC2 Nginx → DjangoNginx가 TLS 종료 후 컨테이너의 loopback 포트 8000으로 전달

아직 연결되지 않은 곳: Vercel rewrite와 HTTPS 원본, EC2 Nginx/TLS, Django 환경변수, RDS 앱 계정. S3: 현재는 비공개 버킷만 준비됨. 이미지 업로드 기능이 구현되면 필요한 prefix에만 앱 IAM 권한을 추가합니다.

B · development 브랜치 코드가 검증된 뒤

GitHub push배포할 코드가 development에 병합됨
CI · quality + test둘 다 성공해야 개발 배포가 이어짐
OIDC → ECRGitHub 임시 권한으로 SHA 태그 이미지 push, digest 고정
SSM → EC2이미지 pull, migration, Compose 실행·healthcheck
개발 앱 확인외부 HTTPS, 로그인·메일·Kakao와 DB 확인
EC2에서 git pull하지 않습니다. 현재 deploy-development.yml은 GitHub Actions가 이미지 빌드·배포를 맡습니다. EC2는 Git 저장소가 아니라 이미지 실행 호스트입니다. Vercel은 client Git 저장소 배포를 따로 처리합니다.

GitHub Actions는 어떤 값으로 AWS에 접근하나요?

결론부터 보면 AWS_DEPLOY_ROLE_ARN은 AWS에서 맡을 IAM 역할을 지정하고, DEVELOPMENT_INSTANCE_ID는 배포할 EC2를 지정합니다. 두 값은 같은 목적이 아니며, 둘 다 비밀번호나 Access Key가 아닙니다.

한 번의 development push가 배포되는 길

GitHub Actionsdevelopment push 후 Quality·Test를 먼저 실행
OIDC ID tokenid-token: write로 이 실행을 증명
AWS STS → deploy role신뢰 조건이 저장소와 development Environment를 확인하고 임시 자격 증명을 발급
ECR push + SSM이미지를 SHA tag로 저장하고 지정한 EC2에 배포 명령 전달
EC2 instance role별도 역할로 ECR에서 image pull 후 Docker Compose로 실행
중요한 경계: GitHub deploy role은 이미지 push와 SSM 배포 명령을 허용합니다. EC2 instance role은 서버가 이미지 pull하는 권한을 가집니다. 두 역할을 하나로 합치지 않습니다. 현재 EC2에는 SSM 권한이 있고, ECR pull 권한은 아직 추가해야 합니다.

이름이 비슷해 보여도 맡은 일은 다릅니다

AWS_DEPLOY_ROLE_ARN“GitHub Actions가 AWS에서 어떤 역할로 행동할까?”에 답합니다. 현재 값은 arn:aws:iam::968579693658:role/traceback-development-deploy. workflow의 role-to-assume에 전달됩니다. ARN은 역할의 주소이고, 그 자체로 로그인 비밀키는 아닙니다.
DEVELOPMENT_INSTANCE_ID“SSM 명령을 어느 EC2로 보낼까?”에 답합니다. 현재 대상은 i-051f85a1ac4e64a2c. GitHub Actions가 이를 INSTANCE_ID로 deploy 스크립트에 넘깁니다. AWS에 인증하거나 권한을 부여하는 값이 아닙니다.
AWS_REGION리소스가 있는 AWS 리전. 현재 ap-northeast-2 (서울)입니다. STS 자격 증명을 받는 호출과 ECR/SSM 요청에 함께 쓰입니다.
ECR_REPOSITORY이미지 저장소 이름 traceback. 계정 ID와 리전이 포함된 전체 주소는 ECR login/build action이 구성합니다.
IAM에서 구분할 두 질문: Trust relationship은 “누가 이 역할을 맡을 수 있나?”를 정합니다. Permission policy는 “맡은 뒤 무엇을 할 수 있나?”를 정합니다. GitHub OIDC provider와 trust policy가 전자, ECR/SSM 정책이 후자입니다. EC2 instance role은 별도의 주체와 별도 권한입니다. 실제 정책 문서는 docs/deployment.md의 OIDC·정책 절에 있습니다.
AWS 계정의 GitHub 배포 역할

traceback-development-deploy

GitHub Actions 실행이 OIDC로 임시 사용합니다. 역할의 Trust relationship은 지정된 GitHub OIDC provider를 신뢰하고, sub를 repo:orange-taco/traceback:environment:development로 제한합니다. 따라서 다른 저장소나 Environment는 이 역할을 맡지 못합니다.

  • 허용: ECR traceback에 이미지 push 및 이미지 조회
  • 허용: 지정된 EC2에 SSM Run Command 전송·결과 조회
  • 불허: IAM 역할 생성/수정, 계정 관리자 권한, 임의 EC2 조작

GitHub workflow는 permissions: id-token: write를 선언하고 aws-actions/configure-aws-credentials에서 이 역할 ARN을 가리킵니다. AWS access key secret은 없습니다.

EC2 인스턴스에 붙는 실행 역할

traceback-development-ec2

인스턴스 프로파일을 통해 EC2 안의 AWS CLI/Docker가 사용합니다. 배포 명령 중 EC2가 ECR에서 이미지를 가져오려면 pull 권한이 필요합니다.

  • 현재 연결됨: AmazonSSMManagedInstanceCore (SSM Agent 관리 통신)
  • 다음에 추가: ECR pull 전용 권한 (ECR login, manifest와 image layer 다운로드)
  • 지금은 부여하지 않음: S3 쓰기 권한. 업로드 코드/경로가 생길 때 필요한 bucket prefix만 허용

배포가 아직 안 되는 이유: GitHub는 ECR에 이미지를 보낼 수 있지만, EC2가 ECR에서 그 이미지를 받을 IAM 권한은 아직 설정하지 않았습니다.

GitHub deploy role에 붙인 Permissions policy

정책은 작업에 필요한 서비스 API와 대상 자원을 묶습니다

ECR 인증ecr:GetAuthorizationToken — Docker가 ECR 로그인 token을 받습니다. 이 API는 repository ARN 하나로 제한할 수 없어 Resource *가 필요합니다.
ECR 이미지 동작저장소 traceback ARN에만 DescribeRepositories, DescribeImages, push에 필요한 layer upload·PutImage 권한을 허용합니다.
SSM 배포 요청ssm:SendCommand를 AWS 관리 문서 AWS-RunShellScript와 개발 EC2 i-051f85a1ac4e64a2c에 함께 범위 지정합니다. SSM을 통해서만 서버 명령이 들어가고 SSH 22는 열지 않습니다.
SSM 결과 확인ssm:GetCommandInvocation은 배포 성공 여부와 출력을 가져옵니다. 현재 이 API 권한은 AWS가 지원하는 리소스 ARN 범위 제한이 어려워 Resource *를 사용합니다.

최종 JSON과 리전/계정/저장소/인스턴스 ARN을 대입하는 예시는 docs/deployment.md에 있습니다. AWS IAM 화면에서 inline policy 이름 traceback-development-deploy-policy를 확인했습니다.

지금까지 실제로 설정한 순서

아래 순서대로 AWS와 GitHub 화면을 설정했습니다. 값은 현재 development 설정이며, production은 별도 계정/역할/Environment를 준비할 때 구성합니다.

GitHub Environment를 준비

저장소 Settings → Environments → development. 사용 가능한 branch를 development 하나로 제한합니다. workflow가 이 Environment를 지정해야 변수와 보호 설정을 읽습니다.

private ECR 저장소 생성

AWS Seoul → ECR → Private repositories에서 traceback 생성. 태그 변경 불가(immutable), 기본 AES-256 암호화. 현재 repository는 비어 있어 첫 성공 배포 전까지 이미지가 없습니다.

GitHub OIDC provider 생성

AWS IAM → Identity providers에 provider URL https://token.actions.githubusercontent.com, audience sts.amazonaws.com 등록. GitHub 실행이 서명한 ID token을 AWS가 검증할 수 있게 연결합니다.

전용 deploy role과 Trust relationship 생성

IAM role traceback-development-deploy의 신뢰 대상은 위 OIDC provider 하나로 둡니다. aud=sts.amazonaws.com와 sub=repo:orange-taco/traceback:environment:development 조건으로 scope를 제한했습니다.

최소 권한 policy 연결

역할에 ECR push/조회와 SSM 명령 권한만 넣었습니다. ECR 동작은 저장소 traceback에 범위 지정, SSM 전송 대상은 development EC2로 제한합니다. Access Key를 만드는 절차는 없습니다.

GitHub Environment 변수 등록

AWS_DEPLOY_ROLE_ARN, AWS_REGION, ECR_REPOSITORY, DEVELOPMENT_INSTANCE_ID를 Environment Variables에 저장했습니다. 전부 배포 위치/자원 식별 값이라 secrets가 아니며 `.env.dev.git`은 기록용 목록입니다.

development branch protection 설정

PR 병합과 Quality, Test 통과를 요구합니다. 승인 review는 0명, force push와 branch deletion은 차단. 현재 “Do not allow bypassing”는 켜지지 않아 repository 관리자에게 우회 권한이 남아 있습니다.

남은 EC2 준비를 끝내고 첫 push 검증

EC2 역할에 ECR pull 권한, Docker/Compose/AWS CLI, 런타임 /opt/traceback/.env, Nginx/TLS가 필요합니다. 준비 후에야 development push에서 OIDC→ECR→SSM 전체 흐름을 실제 확인할 수 있습니다.

휴대폰에서도 읽기 쉬운지 확인

ECR을 쓰면 추가 요금이 드나요?

저장소 자체는 월정액이 아닙니다

ECR은 이미지가 저장된 용량과 인터넷 방향 전송량을 기준으로 과금합니다. 저장 이미지가 아직 없는 현재는 ECR repository 이름만 만들어 둔 데서 이미지 저장 비용이 생기지 않습니다. AWS 가격 페이지 예시는 private image storage USD 0.10/GB-month이며, 새 ECR 고객은 첫 1년 동안 private storage 500 MB/month 무료 혜택이 표시됩니다. 계정별 Free Tier 대상 여부를 Billing에서 확인해야 합니다.

현재 흐름의 큰 비용 요인은 이미지 보관량

같은 서울 리전의 ECR↔EC2 데이터 전송은 AWS 가격표상 무료입니다. GitHub-hosted runner에서 ECR로 push하는 전송도 ECR inbound 과금 대상이 아닙니다. 배포 때마다 SHA tag 이미지가 쌓이므로, 오래된 이미지 보관 정책이 없으면 저장 용량이 누적됩니다. 첫 배포 전 수명주기 정책을 정하되, production 승격·rollback에 필요한 digest를 삭제하지 않도록 해야 합니다.

비용 체크: 지금 만든 ECR은 비어 있고 repository 생성 자체에는 월 정액이 없습니다. 첫 image push부터 저장 용량이 계산됩니다. AWS 크레딧은 청구 상한이 아니므로 Amazon ECR 공식 가격표와 Billing을 확인하세요. 화면에 캡처된 immutable tag 설정은 같은 SHA 이름의 이미지를 덮어쓰지 못하게 해 배포 재현성을 높이지만, 이미지를 자동 삭제하지는 않습니다.

더 깊은 접속 인증/SSM 구조는 SSH와 SSM 학습 가이드, 도메인과 DNS는 DNS 가이드, IP 선택은 개발 IP·도메인 가이드에서 공부합니다. 이 문서는 그 자원들을 CI/CD에 연결하는 전체 흐름을 다룹니다.

배포 코드는 어떤 순서로 읽으면 될까요?

파일 하나가 모든 일을 하는 구조가 아닙니다. Dockerfile이 실행 이미지를 만들고, CI가 검증하며, 환경별 workflow가 이미지 저장과 서버 배포를 고르고, 공통 스크립트가 SSM으로 EC2에 명령을 보냅니다.

1 · Dockerfile로컬 개발용과 운영용 이미지 만드는 법
2 · Compose 파일 2개공통 설정 + 운영 환경 덮어쓰기
3 · ci.ymlPR/push 검사와 CD 호출 조건
4 · deploy-development.ymldevelopment 이미지 build/push 후 EC2 배포
5 · deploy-production.ymldevelopment에서 검증된 동일 이미지 digest 승격
6 · deploy-ec2.shSSM으로 EC2 내부 명령 실행·결과 확인
development와 production 스크립트를 왜 따로 만들지 않나요? 배포 동작은 같습니다. 환경별 workflow가 서로 다른 GitHub Environment, IAM 역할, EC2 인스턴스 ID와 이미지 선택 규칙을 고릅니다. 공통 셸 스크립트를 하나로 유지하면 dev와 prod의 보안 수정이 한쪽에만 반영되는 실수를 막습니다. 단계가 실제로 달라질 때만 공통 함수를 남기고 별도 스크립트로 분리하는 편이 낫습니다.

GitHub Actions가 자동으로 ECR에 올리는 지점

development push에서 ci.yml의 Quality와 Test가 먼저 성공해야 deploy-development.yml이 호출됩니다. 그 안의 docker/build-push-action이 Dockerfile의 production target을 빌드하고 push: true로 ECR에 업로드합니다. 이미지 tag는 커밋 SHA이며, 다음 단계는 tag가 아니라 ECR이 부여한 digest를 EC2에 전달합니다. EC2는 직접 Git pull이나 Docker build를 하지 않습니다.

수동으로 ECR에 push하려면

수동 배포는 로컬 컴퓨터에서 Docker build → ECR push → digest 확인 → SSM 배포 순서입니다. Docker Hub는 이 흐름에 필요 없습니다. 아래 예시는 현재 개발 리전/저장소를 사용합니다. 로컬 AWS Identity Center 프로필이 ECR push 권한을 가져야 합니다. GitHub OIDC용 deploy role은 GitHub token만 신뢰하므로, 로컬 프로필이 그 role을 자동으로 대신 쓰지는 않습니다.

# 반드시 빌드할 커밋의 저장소 상태가 깨끗한지 확인
git status --short
test -z "$(git status --porcelain)" || { echo "Commit or discard local changes before publishing" >&2; exit 1; }

# 로컬 AWS SSO 프로필로 로그인한 다음 ECR 대상을 정함
export AWS_PROFILE=traceback-dev
export AWS_REGION=ap-northeast-2
aws sso login --profile "$AWS_PROFILE"
export AWS_ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"
export ECR_REPOSITORY=traceback
export IMAGE_TAG="$(git rev-parse HEAD)"
export ECR_REGISTRY="${AWS_ACCOUNT_ID}.dkr.ecr.${AWS_REGION}.amazonaws.com"
export IMAGE_URI="${ECR_REGISTRY}/${ECR_REPOSITORY}:${IMAGE_TAG}"

# ECR 로그인, 운영 이미지 빌드, 업로드
aws ecr get-login-password --region "$AWS_REGION" \
  | docker login --username AWS --password-stdin "$ECR_REGISTRY"
docker build --platform linux/amd64 --target production --tag "$IMAGE_URI" .
docker push "$IMAGE_URI"

# 배포에 쓸 불변 digest 조회
export IMAGE_DIGEST="$(aws ecr describe-images \
  --repository-name "$ECR_REPOSITORY" \
  --image-ids "imageTag=$IMAGE_TAG" \
  --query 'imageDetails[0].imageDigest' --output text)"
export APP_IMAGE="${ECR_REGISTRY}/${ECR_REPOSITORY}@${IMAGE_DIGEST}"

# 준비가 끝난 development EC2에 SSM으로 배포
export INSTANCE_ID=i-051f85a1ac4e64a2c
bash .github/scripts/deploy-ec2.sh
수동 실행 전 조건: Docker 플랫폼이 EC2 CPU와 맞아야 해서 현재 t3 계열용으로 linux/amd64를 명시합니다. ECR tag는 immutable이므로 같은 SHA tag를 다시 덮어쓸 수 없습니다. 로컬 IAM 자격에는 ECR push와 SSM 대상/명령 조회 권한이 필요하고, EC2 instance role에는 ECR pull 권한이 필요합니다. 아직 서버 `.env`와 ECR pull 권한이 준비되지 않아 위 명령을 지금 실행해도 첫 배포가 완료되지는 않습니다.

파일별 맡은 일

Dockerfile · 실행 이미지

base에 Python과 고정 버전의 uv를 준비하고, 개발/운영 의존성을 다른 build stage에서 설치합니다. 운영 stage는 개발 도구를 빼고 앱 코드를 복사한 뒤 권한이 제한된 app 사용자로 Gunicorn/ASGI를 실행합니다.

docker-compose.yml · 로컬 개발 기본값

Django 개발 서버와 PostgreSQL을 정의합니다. .:/app은 코드 변경을 컨테이너에서 바로 보는 bind mount입니다. postgres_data는 로컬 DB 데이터가 담기는 이름 있는 Docker volume입니다.

docker-compose_prod.yml · 운영 overlay

기본 Compose 설정에 운영 이미지를 지정하고 개발 서버 명령·DB 의존성을 제거합니다. db: !reset null로 Postgres 컨테이너를 빼고, volumes: !reset []로 소스 bind mount를 제거합니다. 운영 DB는 RDS, 업로드 파일은 S3에 두므로 EC2의 Compose volume에 영구 업무 데이터를 보관하지 않습니다.

.github/workflows/ci.yml · 검사와 갈림길

PR에서는 Quality/Test를 실행하고, main PR에서는 운영 이미지의 컨테이너 smoke test도 실행합니다. development push에서 검사 둘이 성공하면 development workflow를 호출하고, main push에서만 production workflow를 호출합니다.

deploy-development.yml · build/push/development 배포

GitHub OIDC로 개발 deploy role을 맡습니다. ECR tag 규칙을 확인하고, 같은 SHA 이미지가 이미 있으면 재사용합니다. 없으면 운영 target 이미지를 build/push합니다. 이후 ECR digest와 EC2 ID를 공통 스크립트에 넘깁니다.

deploy-production.yml · digest 승격

main의 merge commit에서 development 쪽 부모 SHA를 찾고 해당 커밋의 development 배포가 성공했는지 확인합니다. ECR에서 그 SHA의 digest를 읽고 production EC2로 전달합니다. production에서 이미지를 다시 빌드하거나 ECR push하지 않습니다.

파일 이름 컨벤션: docker-compose.yml은 지금도 사용할 수 있고 이전 Compose 이름과 호환됩니다. Docker 문서에서 기본·권장 이름은 compose.yaml이며, 일반적으로 기본 파일과 환경 overlay를 -f 순서로 합칩니다. 우리 파일명은 기능을 알아보기 쉽고 모든 workflow/EC2 배포 코드에서 일관되게 사용 중입니다. 이름만 바꾸면 배포 스크립트가 이미지에서 꺼내는 경로와 CI·문서 참조도 함께 바꿔야 하므로 지금은 유지합니다. 새 프로젝트를 시작하거나 별도 정리할 때 compose.yaml + compose.production.yaml로 한 번에 바꾸면 됩니다. Docker Compose 파일 병합 공식 안내

deploy-ec2.sh 전체 코드와 읽는 법

이 파일은 이미지를 만들거나 ECR에 push하지 않습니다. GitHub workflow 또는 로컬에서 실행되어 SSM 명령을 보내고, EC2의 ECR pull·Compose 실행 결과를 기다리는 배포 조정 스크립트입니다. dev와 prod가 함께 호출하는 현재 원본입니다.

deploy-ec2.sh 원문 전체 보기 (67줄) 
#!/usr/bin/env bash
set -euo pipefail

# Validate the image and deployment target before making an AWS request.
: "${APP_IMAGE:?APP_IMAGE is required}"
: "${INSTANCE_ID:?INSTANCE_ID is required}"
: "${AWS_REGION:?AWS_REGION is required}"

if [[ ! "$INSTANCE_ID" =~ ^i-[0-9a-f]+$ ]]; then
  echo "INSTANCE_ID must be an EC2 instance ID" >&2
  exit 1
fi

if [[ ! "$AWS_REGION" =~ ^[a-z0-9-]+$ ]]; then
  echo "AWS_REGION contains unsupported characters" >&2
  exit 1
fi

if [[ ! "$APP_IMAGE" =~ ^[0-9]{12}\.dkr\.ecr\.[a-z0-9-]+\.amazonaws\.com/[A-Za-z0-9._/-]+@sha256:[0-9a-f]{64}$ ]]; then
  echo "APP_IMAGE must be an ECR image digest" >&2
  exit 1
fi

registry="${APP_IMAGE%%/*}"
# SSM Run Command accepts one JSON object containing the EC2 shell commands.
commands=(
  "set -eu"
  "cd /opt/traceback"
  "docker compose version --short"
  "aws ecr get-login-password --region $AWS_REGION | docker login --username AWS --password-stdin $registry"
  "docker pull $APP_IMAGE"
  "docker run --rm --entrypoint cat $APP_IMAGE /app/docker-compose.yml > docker-compose.yml.next"
  "docker run --rm --entrypoint cat $APP_IMAGE /app/docker-compose_prod.yml > docker-compose_prod.yml.next"
  "mv docker-compose.yml.next docker-compose.yml"
  "mv docker-compose_prod.yml.next docker-compose_prod.yml"
  "APP_IMAGE=$APP_IMAGE docker compose --env-file .env -f docker-compose.yml -f docker-compose_prod.yml config --quiet"
  "APP_IMAGE=$APP_IMAGE docker compose --env-file .env -f docker-compose.yml -f docker-compose_prod.yml run --rm app python manage.py migrate --noinput"
  "APP_IMAGE=$APP_IMAGE docker compose --env-file .env -f docker-compose.yml -f docker-compose_prod.yml up -d --no-build --wait app"
)
commands_json="$(jq -nc --args '$ARGS.positional | {commands: .}' -- "${commands[@]}")"

# Send the deployment sequence to EC2 through SSM; no SSH session is opened.
command_id="$(aws ssm send-command \
  --instance-ids "$INSTANCE_ID" \
  --document-name AWS-RunShellScript \
  --parameters "$commands_json" \
  --query 'Command.CommandId' \
  --output text)"

# Poll longer than the default AWS CLI waiter because image pulls and migrations
# may take more than 100 seconds on a small development instance.
status=Pending
for ((attempt = 0; attempt < 120; attempt++)); do
  status="$(aws ssm get-command-invocation \
    --command-id "$command_id" \
    --instance-id "$INSTANCE_ID" \
    --query Status --output text 2>/dev/null || true)"
  case "$status" in
    Success|Failed|Cancelled|TimedOut) break ;;
  esac
  sleep 5
done

aws ssm get-command-invocation \
  --command-id "$command_id" \
  --instance-id "$INSTANCE_ID"
test "$status" = Success

1 · 입력값 검사와 digest 고정 (1–24행)

set -e는 실패한 명령에서 중단, -u는 미설정 변수를 오류 처리, pipefail은 파이프 중간 실패도 오류로 처리합니다. 필수 환경변수 세 개와 EC2 ID·리전 형식을 검사하고, APP_IMAGE가 특정 계정/리전 ECR의 @sha256:... 형식인지 검증합니다. 태그보다 내용이 고정된 digest를 받습니다.

2 · EC2 안에서 실행할 명령 목록 구성 (24–40행)

이미지 주소에서 ECR registry 주소를 분리합니다. Bash 배열에 EC2 명령을 한 줄씩 적고, jq --args가 배열을 SSM의 { commands: [...] } JSON으로 바꿉니다. 이 방식은 긴 JSON 문자열 안에서 shell 명령을 조립하던 형태보다 각 원격 명령을 읽기 쉽습니다.

  • EC2에서 /opt/traceback으로 이동하고 Compose가 설치됐는지 확인
  • EC2 instance role의 임시 자격 증명으로 ECR login 후 정확한 digest를 pull
  • pull한 이미지에서 그 커밋의 Compose 파일을 꺼내 임시 파일에 저장한 다음 기존 파일과 교체
  • 서버 `.env`와 두 Compose 파일을 병합해 설정이 유효한지 확인
  • 새 앱 이미지로 DB migration을 실행하고, 새 앱을 올린 뒤 healthcheck가 통과할 때까지 기다림

3 · SSM 명령 전송과 완료 대기 (42–67행)

aws ssm send-command는 shell 접속을 여는 대신 지정 EC2에 Run Command를 보내고 Command ID를 돌려줍니다. 이후 5초 간격으로 최대 120회(10분) 상태를 확인합니다. 마지막으로 표준 출력/오류를 표시하고 최종 상태가 Success인지 검사합니다.

볼륨은 환경마다 다르게 다룹니다

로컬에서 docker compose down을 하면 컨테이너는 내려가지만 postgres_data는 남아 다음 실행에도 DB 데이터가 유지됩니다. docker compose down -v는 이 로컬 DB 볼륨까지 삭제하므로 초기화할 때만 사용합니다. 운영 overlay는 소스 bind mount와 Postgres 서비스를 제거하고 명시적 Docker volume도 비웁니다. 운영 데이터는 RDS/S3에 남고 EC2에는 실행 중인 컨테이너와 내려받은 이미지 layer가 저장됩니다. EC2 디스크 정리는 DB 볼륨 삭제와 별개이며, 과거 이미지가 rollback에 필요한지 확인한 뒤 보관/정리 정책을 둡니다. docker system prune --volumes처럼 volume까지 한꺼번에 지우는 명령은 운영 서버에서 피합니다.

현재 코드에서 남은 운영상 한계

이 스크립트는 배포 실패 시 이전 버전으로 자동 rollback하지 않습니다. Compose 파일을 새 버전으로 바꾼 뒤 config, migration 또는 healthcheck에서 실패할 수 있으므로 실제 첫 배포 후에는 이전 digest 재배포 절차와 migration 복구 기준을 별도로 연습해야 합니다. dev/prod 실행 파일을 복제해 나누는 것보다 이 공통 동작을 하나로 두고 환경별 권한·대상·승인만 분리하는 것이 현재 구조에 맞습니다.

Nginx는 어디에 두는 게 일반적인가요?

Nginx는 HTTP 요청을 받아 다른 서버나 프로세스로 전달하는 웹 서버·reverse proxy입니다. “EC2 안”은 EC2 호스트에서 실행한다는 뜻이고, “앞단 별도”는 Nginx 전용 머신이나 AWS 관리형 Load Balancer가 앱 인스턴스보다 먼저 요청을 받는 구조입니다. 규모와 가용성 요구에 따라 선택합니다.

일반 패턴 비교현재 TRACEBACK 선택: 같은 EC2의 호스트 Nginx
소규모 · 단일 서버

Nginx를 앱 EC2 호스트에 설치

인터넷→EC2 보안 그룹 80/443→Nginx (EC2 host)→127.0.0.1:8000 Docker 앱

요청이 어떻게 흐르나: Vercel이 https://api.dev-traceback.com에 요청합니다. Route 53이 EIP를 알려주고, EC2의 443에서 Nginx가 TLS를 끝낸 뒤 Docker 안의 Django로 전달합니다. Django는 private 경로로 RDS에 연결합니다.

  • 좋은 점: 별도 LB나 Nginx 서버 비용이 없고 구조가 작아 배우기 쉽습니다.
  • 감수할 점: 한 EC2가 장애 나면 Nginx와 앱이 함께 중단됩니다. OS 보안 업데이트, Nginx 설정, 인증서 갱신을 직접 관리합니다.
  • 보안 경계: 외부에는 80/443만 열고 앱 8000은 localhost에만 bind합니다. RDS 5432는 EC2 보안 그룹에서만 허용합니다.

우리 선택: 지금 dev는 이 방식입니다. 배포 스크립트는 docker-compose.yml과 docker-compose_prod.yml을 함께 읽습니다. 기본 파일의 127.0.0.1:8000:8000 게시 설정은 운영 오버레이와 합쳐진 결과에도 남아 있으므로, 호스트 Nginx가 EC2 내부에서 앱에 연결할 통로는 준비되어 있습니다. 이 포트는 loopback에만 묶여 외부 인터넷에 직접 공개되지 않습니다.

같은 EC2 · Nginx도 컨테이너

Nginx를 Docker Compose 서비스로 실행

인터넷→EC2 80/443→Nginx 컨테이너→Docker 내부망의 Django

별도 서버를 만드는 방식은 아닙니다. 호스트 Nginx처럼 EC2 한 대에서 동작하지만, Nginx 프로세스도 컨테이너로 포장해 Compose가 앱과 함께 관리합니다.

  • 좋은 점: Nginx 버전과 설정을 이미지/코드로 관리하고 호스트 패키지 설치를 줄일 수 있습니다.
  • 감수할 점: Compose 네트워크와 인증서 파일·갱신, Nginx 컨테이너 재시작 의존성까지 직접 설계해야 합니다.
  • 중요: 컨테이너로 옮겨도 장애 경계와 서버 비용은 여전히 EC2 한 대 기준입니다.

현재 선택은 아님: 이 프로젝트의 Nginx 예시는 호스트에 설치하는 구성을 전제로 합니다. 컨테이너 방식으로 바꾸려면 Compose 네트워크와 TLS 보관·갱신을 함께 바꿔야 합니다.

여러 앱 서버 · 확장/가용성

관리형 ALB를 앱 EC2 앞에 둠

인터넷→ALB 443 + 인증서→target group / health check→EC2 앱들

요청이 어떻게 흐르나: AWS Application Load Balancer가 외부 HTTPS 연결을 받고 인증서를 사용해 TLS를 끝낼 수 있습니다. Listener 규칙이 건강한 target에 요청을 전달하고, 여러 EC2·가용 영역으로 분산할 수 있습니다.

  • 좋은 점: 인스턴스 여러 대로 요청 분산, health check, host/path routing, 인증서 관리를 AWS에서 제공받습니다.
  • 감수할 점: ALB 시간·처리량 요금과 대상 보안 그룹, target group, listener 등 설정이 추가됩니다. 앱 인스턴스 한 대만 두면 그 인스턴스 장애를 해결하지 못해 고가용성이 완성되지는 않습니다.
  • Nginx는 필수 아님: 앱 앞의 라우팅과 TLS를 ALB가 담당하면 Django/Gunicorn으로 직접 전달할 수 있습니다. 앱별 특별한 proxy 설정이 필요하면 ALB 뒤에 Nginx를 둘 수 있지만, 두 겹으로 둘 이유가 있는지 확인합니다.

일반적인 사용 시점: 여러 EC2로 수평 확장하거나 가용 영역 간 장애 대응이 필요할 때 선택합니다. AWS는 ALB를 대상 그룹과 health check를 사용해 여러 target으로 HTTP/HTTPS를 라우팅하는 관리형 서비스로 설명합니다.

특별한 네트워크 요구

Nginx 전용 EC2를 따로 운영

인터넷→Nginx 전용 EC2→private 앱 EC2→RDS

요청이 어떻게 흐르나: 공개 프록시 서버가 TLS와 reverse proxy를 담당하고 앱 서버는 private subnet에 둘 수 있습니다. 이때 프록시 서버와 앱 서버 사이의 보안 그룹 규칙·장애 대응도 직접 설계해야 합니다.

  • 가능한 이유: 프록시 계층을 앱 호스트와 분리하거나 여러 내부 서비스에 공통으로 붙이는 특수한 요구가 있을 수 있습니다.
  • 감수할 점: EC2 한 대와 운영 대상이 추가되고, 그 Nginx가 단일 장애 지점이 될 수 있습니다. 고가용성을 얻으려면 프록시도 여러 대와 앞단 분산이 필요합니다.
  • 실무 판단: AWS에서 단순히 “서버를 나누고 싶다”는 이유라면 전용 Nginx EC2부터 늘리기보다 ALB 같은 관리형 진입점이 요구에 맞는지 비교합니다.

우리 현재 선택은 아님: dev는 EC2 한 대이고 앞단 전용 인스턴스를 따로 두지 않습니다.

TLS 종료란? 브라우저/Vercel과 HTTPS로 암호화된 연결을 Nginx나 ALB가 받아 인증서를 제시하고 복호화하는 위치를 말합니다. 현재 계획에서는 EC2 호스트 Nginx가 인증서를 사용합니다. ALB 패턴에서는 보통 HTTPS listener에 인증서를 연결합니다. 한 연결의 어느 지점에서 TLS가 끝나는지 알아야 Django에 올바른 scheme/host 정보를 전달하고 secure cookie·CSRF를 검증할 수 있습니다.
Compose 파일을 왜 두 개 읽나요? 기본 파일은 로컬/공통 앱의 포트와 네트워크를 정의하고, docker-compose_prod.yml은 이미지·운영 보안·health check·DB 제거 설정을 덧씌웁니다. 배포 스크립트가 두 파일을 docker compose -f … -f …로 함께 적용합니다. 따라서 한 파일만 보고 최종 포트가 없다고 판단하면 안 됩니다. 병합된 결과는 docker compose … config로 확인합니다.
아직 필요한 실제 작업: 네트워크 포트 통로는 코드에 있습니다. 하지만 EC2에 Nginx 설치·설정, 80/443 인바운드와 localhost 8000 경계 확인, TLS 인증서 발급·갱신, 실제 HTTPS 요청 검증은 아직 남았습니다.

dev/prod 서버를 어떻게 운영할까요?

저장소의 현재 설계와 GitHub Actions는 dev·prod 각각의 서버와 DB를 기준으로 만들어져 있습니다. 아래 선택지를 눌러 비용과 운영 영향을 비교하세요.

권장: ① 현재 확정 설계대로 진행
개발 중인 서버에는 개발 코드만 배포합니다. 안정화 시 별도 prod EC2·RDS·Vercel 프로젝트를 만들고, 기존 CI/CD가 검증한 이미지 digest를 승격합니다.

① 개발은 개발대로 권장

흐름: 지금은 dev 환경을 완성하고 테스트합니다. 서비스 공개 준비가 되면 독립된 prod 환경을 구축합니다.

  • 기존 feature → development → main 흐름과 CI/CD를 유지
  • 개발 실패가 운영 고객에게 바로 영향 주지 않음
  • 당장은 prod EC2/RDS를 만들지 않아 비용 지출을 미룸
  • prod 구축 후에는 서버·DB 등 운영비가 추가됨

② 기존 dev 인스턴스를 prod로 전환

흐름: 이 서버를 운영 서버로 바꾸고 dev 자동 배포는 멈춥니다.

  • 당장 별도 prod EC2를 만들지 않으므로 인스턴스 비용을 미룸
  • dev에 push할 때 운영 서버가 바뀌지 않게 workflow/환경값을 먼저 바꿔야 함
  • 테스트 공간이 사라져 다시 dev를 만들면 이중 작업
  • RDS와 Vercel 환경 분리도 다시 설계해야 함

지금의 `DEVELOPMENT_INSTANCE_ID` 배포 경로를 그대로 두면 개발 코드가 운영 서버로 갈 수 있어 현재 구조와 맞지 않습니다.

③ 한 EC2에서 dev·prod 같이 실행

흐름: 한 호스트의 별도 Compose stack·환경변수·도메인으로 두 앱을 운영합니다.

  • EC2 한 대 사용으로 호스트 비용을 줄일 수 있음
  • dev/prod별 Docker 포트, Nginx route, DB 접근, 배포 workflow를 직접 분리해야 함
  • 현재 t3.micro의 CPU·메모리와 장애 지점을 공유
  • 호스트 장애나 잘못된 배포가 양쪽 환경에 영향

서버는 한 대라도 DB·자격증명·로그인 도메인은 분리해야 하고, 지금 CI/CD도 수정해야 합니다.

비용 관점: 옵션 ①은 지금 prod 인프라 비용을 시작하지 않는 방법입니다. RDS를 멈춰도 스토리지·백업 비용은 남고, 현재 기록된 생성 추정은 인스턴스와 20 GiB 저장소만 월 USD 20.87입니다. AWS 크레딧은 지출 상한이 아닙니다. S3는 비어 있는 동안 비용이 작지만 요청·저장·전송에 따라 달라질 수 있습니다.

첫 개발 배포 순서

아래는 추천안 ① 기준입니다. 비용이 생기는 AWS 변경이나 공개 엔드포인트 설정은 각 단계에서 실제 계정과 요금을 확인합니다.

운영 모드를 먼저 정하고 배포 코드를 확인

Dev 서버를 dev 전용으로 유지합니다. 로컬 backend/client 변경을 `development`에 반영할 계획이라면 해당 브랜치 상태와 CI를 확인합니다. 서버에서 저장소를 pull하는 작업은 하지 않습니다.

  • CI quality/test 녹색인지 확인
  • 개발 deployment GitHub Environment 및 AWS OIDC 값 준비
  • main에 직접 배포하거나 dev/prod 인스턴스 ID를 섞지 않기

EC2 실행 기반과 최소 권한 설정

인스턴스 역할에 기존 SSM 권한과 ECR pull 권한이 모두 필요합니다. EC2에 Docker Engine, Compose v2, AWS CLI v2를 준비하고 `/opt/traceback`을 만듭니다.

  • 현재 보안 그룹: 웹 80/443 허용, SSH 22 미개방
  • ECR private repository는 immutable image tag로 준비
  • GitHub OIDC provider와 개발 전용 deploy role 생성; 장기 AWS 키를 GitHub에 넣지 않음
  • RDS는 앱 마이그레이션/테스트 동안만 켜고 종료 후 중지

API 도메인과 reverse proxy 연결

이미 준비한 api.dev-traceback.com의 요청을 EC2 안의 Django 앱까지 전달해야 합니다. 현재 선택은 호스트 Nginx가 TLS/HTTPS를 처리하고 같은 EC2의 Docker 앱으로 proxy하는 방식입니다.

  • Compose 기본 파일의 localhost publish와 운영 오버레이를 함께 배포합니다. 병합된 포트는 127.0.0.1:8000이라 Nginx는 연결할 수 있고 외부 사용자는 직접 접근하지 못합니다.
  • Nginx가 /_allauth, /accounts, /api 요청의 경로를 보존해 upstream으로 전달
  • X-Forwarded-Proto: https와 원래 Host를 Django에 전달해 HTTPS cookie/CSRF 동작을 검증
  • 대안은 Nginx 컨테이너 또는 ALB입니다. 같은 EC2의 Nginx 컨테이너는 배포 방식이 달라지고, ALB는 별도 AWS 서비스와 비용이 추가됩니다.

앱용 DB 사용자와 EC2 비밀값 준비

RDS master password를 앱 런타임에 재사용하지 말고, Django용 DB 사용자·DB를 분리합니다. 비밀값은 로컬 Git 파일이나 Vercel frontend에 두지 않습니다.

  • 각 EC2의 미추적 파일: /opt/traceback/.env, 권한 600
  • dev 설정은 DJANGO_SETTINGS_MODULE=config.settings.development; 현재 코드에서 DEBUG=False
  • TRACEBACK_DATABASE_URL은 private RDS endpoint와 앱 DB 계정 사용
  • FRONTEND_BASE_URL은 Vercel 개발 origin; Django secret, SES, Kakao 값은 환경별 별도 보관
  • 환경변수 이름과 목적은 이 문서의 환경변수 절에서 확인

GitHub Environment와 첫 배포 설정

development Environment와 보호된 development 브랜치는 설정 완료. GitHub가 이 저장소의 OIDC token으로 deploy role을 맡고, SHA-tag 이미지를 ECR에 push한 뒤 DEVELOPMENT_INSTANCE_ID로 지정한 EC2에 SSM 명령을 보냅니다.

  • AWS_REGION=ap-northeast-2 · 리전
  • ECR_REPOSITORY=traceback · private image repository
  • AWS_DEPLOY_ROLE_ARN=arn:aws:iam::968579693658:role/traceback-development-deploy · OIDC로 맡는 IAM role 주소
  • DEVELOPMENT_INSTANCE_ID=i-051f85a1ac4e64a2c · 배포 명령 대상 EC2

.env.dev.git은 기록용입니다. GitHub가 자동으로 읽지 않으므로 저장소 Settings → Environments → development에 별도로 입력합니다. 정적 Access Key는 등록하지 않았습니다.

서버 배포 뒤 Vercel 경로 연결

client repo의 vercel.ts는 DJANGO_ORIGIN이 설정되면 필요한 외부 rewrite를 구성합니다. 현재 Vercel 값은 비어 있어 rewrite 목록이 비어 있고, .env.dev 파일도 Vercel에 자동 업로드되지 않습니다.

  • FRONTEND_ORIGIN: Django가 redirect/CSRF 검증에 사용하는 공개 프런트 origin
  • DJANGO_ORIGIN=https://api.dev-traceback.com: HTTPS API가 준비된 뒤 dev 전용 Vercel 프로젝트의 Production Environment에 등록합니다. 이 프로젝트는 GitHub의 development 브랜치를 Vercel의 Production 배포로 연결했습니다.
  • 환경변수 변경 후 새 배포를 만들어 적용
  • /_allauth, /accounts, /api rewrite와 cookie/CSRF/Kakao callback을 브라우저에서 검증

외부에서 인증·DB·메일을 검증하고 끄기

개발용 Vercel 주소에서 설정 endpoint, 이메일 가입/인증, 로그인/로그아웃, CSRF 변경 요청, Kakao callback과 계정 연결 해제를 확인합니다.

  • Vercel에서 /_allauth/browser/v1/config가 200으로 오고 Django에서 DB 응답
  • HTTPS cookie, proxy host/protocol, Django allowed hosts와 CSRF 동작 확인
  • 외부 HTTP/HTTPS에서 앱만 노출되는지 확인; RDS는 계속 private
  • RDS는 테스트 종료 후 중지. S3 업로드 IAM은 기능이 생길 때만 최소 prefix 권한으로 추가

처음 나오는 네트워크 용어

먼저 단어를 익히면 위의 요청 그림을 따라가기 쉬워집니다. 일반 네트워크 용어와 AWS에서 붙인 이름을 함께 적었습니다.

일반 네트워크 용어

Reverse proxy · 역방향 프록시
사용자 요청을 먼저 받은 뒤 내부 앱 서버로 대신 전달하는 서버입니다. 이 구성에서는 Nginx가 해당 역할을 합니다.
Upstream · 전달 대상
프록시가 요청을 넘기는 다음 서버입니다. 여기서는 Django 앱의 127.0.0.1:8000입니다.
Loopback · 자기 자신 주소
127.0.0.1은 해당 컴퓨터 자신을 가리킵니다. EC2 안의 Nginx와 앱 사이에서만 포트를 열 때 씁니다.
TLS 종료
HTTPS 암호화를 풀고 인증서를 제시하는 지점입니다. 현재 계획에서는 EC2의 Nginx가 처리합니다.
인바운드 / 아웃바운드
보안 경계로 들어오는 연결 / 그 경계에서 밖으로 나가는 연결입니다. 인터넷의 443 요청은 인바운드이고, EC2가 RDS 5432로 접속하는 것은 아웃바운드입니다.

AWS 및 Docker 용어

Security Group · 보안 그룹
EC2나 RDS의 가상 방화벽 규칙입니다. 포트와 허용할 출발지/대상을 지정합니다.
ALB Listener · 수신기
ALB가 어떤 포트/프로토콜(예: HTTPS 443)을 받을지 정의합니다.
Target group · 대상 그룹
ALB가 요청을 전달할 앱 서버 묶음과 상태 확인 규칙입니다.
Health check · 상태 확인
앱이 요청을 처리할 수 있는지 주기적으로 검사해 정상 대상을 고르는 절차입니다.
Compose overlay · 설정 덧씌우기
여러 Compose 파일을 순서대로 합쳐 환경별 최종 구성을 만듭니다. 뒤 파일은 앞 설정을 추가하거나 바꿀 수 있습니다.

환경변수는 저장 위치마다 목적이 달라요

같은 값 이름이 있더라도 어디에 넣는지와 누가 읽는지 구분합니다. 절대 secret 값을 이 문서나 Git에 적지 않습니다.

Vercel · 개발 프런트

FRONTEND_ORIGIN
Django가 redirect/CSRF에 사용하는 공개 Vercel origin. client repo의 `.env.dev`는 로컬 참고값입니다.
DJANGO_ORIGIN
백엔드 HTTPS origin. `.env.dev`에서는 비어 있고, HTTPS가 준비된 뒤 Vercel 프로젝트에 입력.
Vercel Environment
이 dev 전용 프로젝트의 Production branch가 development입니다. 따라서 변수는 Vercel 프로젝트의 Production Environment에 등록합니다. Git branch 이름과 Vercel environment 이름은 같은 개념이 아닙니다.
비밀값 구분
DJANGO_ORIGIN은 주소라 secret이 아닙니다. DB 암호나 Django/Kakao/SES 비밀값은 프런트 변수에 넣지 않습니다.

비용과 안전 기준

초기 고정비 줄이기

  • 당장은 EC2 1대, Single-AZ RDS, NAT Gateway 없음, ALB 없음
  • RDS는 개발/테스트 때 켜고 끝난 뒤 중지. 중지 중에도 storage/backup 요금이 남음
  • EC2 stop은 시간 비용을 줄일 수 있지만 public IPv4가 바뀔 수 있어 DNS와 TLS origin에 영향
  • 현재 문서의 RDS 생성 추정 USD 20.87/월은 RDS instance + 20 GiB storage만이며 나머지 요금은 별도
  • ECR repository 자체는 월 정액이 아니고 이미지 저장량·인터넷 전송에 따라 과금; 빈 repo에는 저장 이미지 비용 없음
  • AWS credit은 bill cap이 아님. 실제 Billing과 Budget alert를 확인

인터넷에 내보내기 전에

  • Django DEBUG=False; secret/key는 EC2 파일에만 보관
  • RDS public access 비활성, 5432 source는 개발 EC2 security group만 허용
  • EC2 inbound는 HTTPS 443 및 필요한 인증서 발급용 HTTP 80만; SSH 22는 열지 않음
  • Vercel→API TLS와 OAuth callback이 검증되기 전 로그인 기능이 준비됐다고 간주하지 않음
  • DB migration 전에 RDS backup/restore 지점 확인
