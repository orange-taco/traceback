질문 01

브라우저는 주소를 입력받고 어디로 갈까요?

www.google.com은 사람이 읽기 좋은 도메인 이름입니다. IP 주소는 네트워크에서 목적지를 식별하는 숫자 주소입니다. 브라우저가 서버에 연결하려면 이 주소가 필요합니다. DNS(Domain Name System)는 이름에 연결된 주소와 다른 정보를 찾는 분산 체계입니다.

주소창에 www.google.com→DNS로 IP 찾기→IP 확보→그 IP의 웹 서버에 연결
https://www.google.com /경로

https://는 웹 연결 방식, www.google.com은 IP를 찾아야 할 호스트 이름입니다. DNS가 찾는 것은 웹페이지 내용이 아니라 이 이름에 대한 주소 정보입니다.

질문 02

IP를 매번 처음부터 찾을까요?

이미 받은 답을 잠시 보관하는 곳이 있습니다.

캐시(cache)는 전에 찾은 DNS 답의 임시 사본입니다. 답이 있으면 바로 돌려주고, 없거나 유효 시간이 끝났으면 다음 단계로 갑니다.

1브라우저구현에 따라 자체 DNS 캐시를 확인있으면 연결
2OS로컬 설정(hosts 등)과 DNS 캐시를 확인있으면 브라우저에 반환
3재귀 DNS ResolverISP·공용 DNS 등이 운영하며 여러 DNS 서버에 대신 질문캐시가 없으면 Root부터 조회
4권한 DNS의 원본 레코드Resolver가 Root와 TLD의 안내를 따라 찾는 정보최종 A 답 제공
TTL은 DNS 답을 캐시에 보관할 수 있는 유효 시간입니다. 만료되면 필요한 답을 다시 묻습니다.

브라우저·OS·Resolver 캐시는 임시 사본이고, 권한 DNS의 레코드는 도메인 관리자가 설정한 원본 답입니다. 브라우저·OS별 캐시 구현과 실제 확인 순서는 다를 수 있습니다.

질문 03

캐시에 없으면 무엇을 물어볼까요?

이름 끝의 점은 무엇인가요?

DNS에서 www.google.com.의 마지막 .은 이름 계층의 맨 위인 Root를 뜻합니다. 주소창에서는 보통 생략하지만, DNS의 완전한 이름을 적으면 끝에 붙습니다.

www호스트.google도메인.comTLD.Root

표기상 왼쪽부터 읽지만, DNS 관리 계층은 오른쪽 Root에서 .com, google.com으로 내려갑니다.

“A 레코드”는 무엇인가요?

DNS는 이름마다 여러 종류의 레코드(record)를 저장합니다. A는 이름에 대응하는 IPv4 주소를 묻는 유형입니다. IPv4와 IPv6는 IP 주소를 적는 두 형식입니다.

AIPv4 주소
예: 142.x.x.x
AAAAIPv6 주소
NS담당 DNS 서버의 이름
CNAME다른 이름을 가리키는 별칭

이 그림은 A 조회 하나를 따라갑니다. 실제 브라우저는 IPv6의 AAAA도 조회할 수 있습니다.

질문 04

“DNS에 묻는다”는 실제로 무엇을 보내나요?

패킷은 네트워크로 보내는 작은 데이터 단위입니다. Query는 질문 패킷, Response는 답 패킷입니다. Resolver는 서버의 IP 주소와 53번 포트로 Query를 보냅니다. 포트는 같은 서버에서 DNS 서비스를 찾아가는 번호입니다.

→ DNS Query 예시목적지: Root DNS IP:53QNAME: www.google.com.QTYPE: A
← DNS Response 예시출발지: Root DNS IP:53내용: .com 담당 DNS의 NS 정보받는 곳: Resolver
재귀 질의 · 최종 답까지 부탁OS의 stub → 재귀 Resolverstub은 OS 쪽의 간단한 DNS 요청 담당입니다. 최종 답이나 오류를 Resolver에게 기대합니다.
반복 질의 · 아는 만큼만 답해줘Resolver ↔ Root
Resolver ↔ TLD
Resolver ↔ 권한 DNSResolver가 각 서버에 새 Query를 보냅니다. 서버는 최종 답 또는 더 가까운 DNS의 위임 정보를 답합니다.

QNAME은 묻는 이름, QTYPE은 원하는 레코드 종류입니다. 위임(referral)은 “그 이름에 더 가까운 담당 DNS는 여기”라는 응답입니다. “다음 서버로 간다”는 포인터 이동이 아니라 Resolver가 응답을 읽고 다른 IP로 새 패킷을 보낸다는 뜻입니다.

질문 05

Resolver는 첫 DNS 서버의 IP를 어떻게 알까요?

Resolver가 알고 시작하는 것

캐시에 답이 없으면 Resolver가 여러 DNS 서버를 차례로 조회합니다. Root DNS는 DNS 계층 맨 위의 Root zone을 담당하는 권한 서버입니다. 그 주소는 Root Hints 목록으로 이미 알고 있습니다.

따라서 www.google.com의 IP를 몰라도 첫 Query의 목적지 IP를 정할 수 있습니다.

이미 아는 것Root DNS 서버들의 이름과 IP아직 모르는 것www.google.com의 최종 IP

Root Hints = 첫 목적지 주소록

Resolver 소프트웨어에는 Root DNS의 이름과 주소 목록이 미리 포함되거나 설정되어 있습니다. Root를 찾기 위해 DNS 조회를 다시 시작할 필요가 없습니다.

A-root → 198.41.0.4
B-root → 170.247.170.2
C-root → 192.33.4.12
... M-root까지

IPv4 주소는 IANA 목록의 예시입니다. Resolver는 이용 가능한 Root 서버 IP 중 하나를 첫 DNS 패킷의 목적지로 선택합니다.

같은 Root IP에 물리 서버가 여러 대라면?

Anycast는 같은 Root 서비스 IP를 여러 물리 인스턴스가 광고하는 방식입니다. 인터넷의 BGP 라우팅이 네트워크 경로를 골라 패킷을 한 인스턴스로 보냅니다. Root Hints에는 출발할 IP가, Anycast에는 그 IP의 실제 도착 경로가 관련됩니다.

Root Hints의 A-root IP→BGP 경로 선택→Root 인스턴스 한 대에 도착

A-root ~ M-root는 13개의 논리적 식별자이지 전 세계 물리 서버 13대라는 뜻이 아닙니다. 지리적으로 가장 가까운 서버가 항상 선택되는 것도 아닙니다. 도시별 배치는 두 번째 탭의 개념도에서 봅니다.

질문 06

왜 Root, .com, google.com 순서로 물을까요?

DNS는 한 서버가 모든 도메인의 IP를 보관하는 구조가 아닙니다. 각 계층이 자기 아래를 담당하는 DNS 서버를 알려주고, 마지막 권한 DNS가 호스트 레코드를 답합니다.

Root ..com 담당 DNS를 알려줌
.com TLDgoogle.com 담당 DNS를 알려줌
google.com 권한 DNSwww의 레코드를 답함
www.google.comA 레코드 = IPv4 예시

TLD는 .com, .net, .kr처럼 이름 끝 쪽의 최상위 도메인입니다. TLD DNS는 그 TLD의 위임 정보를 답합니다. 권한 DNS(Authoritative DNS)는 맡은 영역의 원본 레코드를 관리합니다. NS는 담당 DNS의 이름이고, 다음 DNS의 IP가 필요할 때 glue(NS의 주소를 함께 알려주는 정보)가 위임 응답에 들어올 수 있습니다.

재귀 Resolver · 대신 찾아주는 쪽캐시를 확인하고 Root·TLD·권한 DNS에 새 질문을 보내 최종 답을 모읍니다.
권한 DNS · 맡은 zone을 답하는 쪽그 zone의 원본 레코드를 제공하거나 아래 담당 DNS의 위임을 답합니다. Root와 TLD도 각각 자기 zone의 권한 DNS입니다.

Root는 .com → .com TLD DNS 같은 위임을 관리합니다. google.com → 웹 서버 IP를 Root가 저장하지 않습니다.

Zone과 레코드 유형은 어떻게 다른가요?

Zone은 한 권한 DNS가 책임지고 제공하는 DNS 데이터 범위입니다. Root zone, .com zone, google.com zone이 이 그림의 예입니다. 레코드 유형은 그 안의 한 정보가 무엇을 뜻하는지(A, NS 등)입니다.

정방향 zone이름 → 주소·다른 레코드 조회
역방향 zoneIP → 이름을 PTR 레코드로 조회
Primary zone원본을 관리·수정하는 권한 데이터
Secondary zone전송받은 복사본으로 응답하는 권한 데이터

정방향/역방향은 무엇을 조회하는지, Primary/Secondary는 권한 데이터를 어떻게 운영하는지를 나누는 서로 다른 기준입니다. 둘 다 권한 DNS로 응답할 수 있습니다.

질문 07

IP를 찾으면 웹페이지가 바로 오나요?

DNS는 어디로 연결할지 알려줍니다. 그다음 브라우저가 그 IP의 웹 서버와 별도 연결을 만들어 페이지를 요청합니다.

IP 확보→TCP 연결→TLS→HTTP 요청→서버 응답

TCP는 서버와 통신 경로를 만들고, TLS는 HTTPS 통신을 암호화합니다. HTTP 요청은 원하는 웹페이지나 데이터를 서버에 요청하는 메시지입니다. DNS 서버가 이 요청을 대신 전달하지 않습니다.

이제 캐시가 비어 있다고 가정하고, Resolver가 Root → .com → 권한 DNS에 보내는 실제 패킷을 따라갑니다. 각 파란 Query 뒤에는 초록 Response가 돌아옵니다.

각 캐시 항목은 자체 TTL을 가지며, 만료되면 필요한 단계부터 다시 질의합니다. OS·브라우저도 별도 캐시를 둘 수 있습니다.

위임 응답의 NS와 주소

응답은 다음 서버의 NS 이름을 알려줍니다. 다음 질의를 보내려면 그 서버의 IP도 필요합니다. 필요한 주소가 glue 등으로 응답에 포함될 수 있고, 충분하지 않으면 Resolver가 NS 이름의 주소를 별도로 조회합니다.

DNS 다음은 실제 웹 접속

DNS가 돌려준 IP는 웹 서버 연결의 목적지입니다. DNS 서버가 HTTP 요청을 대신 전달하지 않습니다.

IP 확보→TCP 연결→TLS→HTTP 요청→서버 응답

도메인을 어디서 등록하고 DNS를 어디서 관리할지, 그리고 개발 서버 IP 변경을 어떻게 다룰지 비교합니다.

운영 01

도메인 등록과 DNS 관리는 무엇이 다른가요?

도메인 등록업체(Registrar)는 도메인의 등록 기간·갱신·결제를 관리합니다. DNS 관리업체는 www와 api 같은 이름이 어디로 연결되는지 레코드를 관리합니다. 두 역할을 같은 회사에 맡길 수도, 나눌 수도 있습니다.

등록업체 · 누구에게 비용을 내나?도메인을 한 곳에서 등록하고, 갱신비도 그곳에 냅니다.
DNS 관리업체 · 어디에서 주소를 설정하나?권한 DNS에서 NS·A 등 레코드를 관리합니다.
TRACEBACK 선택Route 53에서 dev-traceback.com 등록·갱신→AWS가 등록 상태·갱신을 관리→Route 53 hosted zone에서 DNS 레코드 관리
분리 가능다른 등록업체에서 구매·갱신→등록업체에서 NS를 Route 53로 변경→Route 53에서 DNS 관리

플랫폼은 같은 일을 하나요?

초록 테두리는 현재 선택한 조합입니다. 등록업체는 이름과 갱신을, 권한 DNS 업체는 레코드를, 프록시는 웹 요청 경로를 맡습니다.

AWS Route 53 · 현재 선택

도메인 등록 지원 TLD는 AWS에서 등록하고 연장

DNS 관리 hosted zone과 레코드를 AWS에서 관리(Hosted zone 요금 별도)

웹 프록시/CDN Route 53 DNS 자체는 제공하지 않음. CloudFront는 별도 서비스

잘 맞는 점 AWS 콘솔·IAM·자동화와 한 계정에서 연결하기 쉬움

Cloudflare

도메인 등록 Registrar 등록/이전 지원 TLD에서 가능

DNS 관리 권한 DNS 제공. Cloudflare Registrar 도메인은 Cloudflare 네임서버를 써야 함

웹 프록시/CDN 프록시를 켜면 요청이 Cloudflare를 거쳐 원본 서버로 감

잘 맞는 점 DNS와 웹 보호·캐시를 함께 쓰고 싶을 때

가비아 · 등록업체 예시

도메인 등록 구매·갱신·국내 결제와 계정 관리를 맡김

DNS 관리 가비아 DNS를 쓰거나 NS를 Route 53/Cloudflare로 위임 가능

웹 프록시/CDN 도메인 등록만으로 프록시가 생기지는 않음

잘 맞는 점 국내 등록·결제·고객지원이 우선이고 DNS는 분리하고 싶을 때

예를 들어 “가비아 등록 + Route 53 DNS”는 가비아에서 한 번 등록한 뒤, 가비아 도메인 설정의 NS를 Route 53 값으로 바꾸는 조합입니다. “Route 53 등록 + Cloudflare DNS/프록시”도 가능하지만, 등록을 Route 53에 두고 네임서버를 Cloudflare로 위임하는 별도 구성입니다. 공급자와 상품별 TLD·기능·가격 조건은 등록 시점에 확인하세요.

도메인은 한 번만 등록합니다. 등록은 도메인 이름의 사용권을 연 단위로 확보하는 일이고, DNS 관리는 그 이름 아래 레코드가 어디를 가리킬지 정하는 일입니다. Route 53에서 등록하면 Route 53이 등록업체이자 DNS 관리업체가 됩니다.

AWS Route 53는 도메인 등록과 권한 DNS를 제공하지만 웹 요청을 대신 전달하는 프록시/CDN은 아닙니다. Cloudflare는 DNS 관리 외에도 프록시·캐시·보안 기능을 제공합니다. Cloudflare 프록시를 쓰려면 Cloudflare가 권한 DNS가 되도록 등록업체에서 네임서버를 바꿔야 합니다. Route 53 hosted zone에는 월 요금이 따로 있습니다. 가격과 지원 TLD는 등록 전 확인하세요.

TRACEBACK 사례: dev-traceback.com은 Route 53에서 ACTIVE 상태이고 등록 네임서버와 public hosted zone이 일치합니다. API용 api.dev-traceback.com A 레코드는 EIP 3.34.78.140을 가리킵니다. DNS 설정이 끝났다는 것은 이름이 IP를 찾는다는 뜻입니다. HTTPS 인증서, Nginx, API 애플리케이션까지 준비됐다는 뜻은 아닙니다. 현재 API 서버는 아직 배포 전입니다. 우리 EIP와 도메인 설정의 자세한 설명 →

운영 02

고정 IP와 유동 IP 중 무엇을 쓰고, 주소 변경은 어떻게 자동화하나요?

고정 IP는 재시작 뒤에도 같은 공인 주소를 쓰도록 예약한 주소입니다. AWS에서는 보통 Elastic IP(EIP)를 뜻합니다. 유동 공인 IP는 EC2를 중지했다가 시작하면 새 주소를 받을 수 있습니다. Development EC2는 DNS 주소를 안정적으로 유지하기 위해 EIP를 사용하기로 했습니다.

고정 IP · Development 선택

DNS 레코드를 계속 같은 IP에 둘 수 있어 운영이 단순합니다. 실행 중 기본 공인 IPv4와 요금이 같고, EC2 중지 중에도 시간당 요금이 발생합니다.

유동 IP

EC2를 중지하면 기본 IP가 반납되어 그 시간의 공인 IPv4 요금이 없습니다. 다시 켜면 IP가 달라질 수 있어 DNS 갱신 자동화가 필요합니다.

요금 비교: AWS 공인 IPv4는 IP 하나당 시간당 USD 0.005입니다. 한 달 내내 연결해 두면 약 USD 3.60~3.65이며, 실행 중에는 기본 IP와 EIP 요금이 같습니다. EIP는 EC2가 중지되어도 연결을 유지하며 계속 과금됩니다.

EC2가 stopped → running→EventBridge가 시작 이벤트를 받음→AWS Lambda가 EC2의 현재 공인 IPv4를 조회→Route 53 ChangeResourceRecordSets로 예: api.dev-traceback.com A 레코드를 UPSERT→DNS TTL 만료 뒤 새 IP로 접속

유동 IP라면 왜 자동화가 필요한가? EC2를 중지하면 기본 공인 IP는 반납되고, 다시 시작할 때 새 IP가 배정될 수 있습니다. DNS A 레코드가 예전 IP에 남으면 도메인이 이전 주소를 계속 알려줍니다. 시작 이벤트 자동화는 현재 IP와 레코드를 맞춰 줍니다.

Development 설정 완료: Route 53에 도메인을 등록하고 EIP 3.34.78.140을 dev EC2에 연결했습니다. api.dev-traceback.com A 레코드도 만들었습니다. Nginx·TLS·백엔드 앱은 아직 배포 전이며, EIP는 EC2 중지 중에도 요금이 발생합니다.

AWS 요금은 VPC 공인 IPv4 요금표를 확인하세요. AWS는 사용 중인 공인 IPv4와 유휴 IPv4 모두 시간당 USD 0.005로 안내합니다.

운영 03

프런트와 API 서버는 왜 이름이 따로 있나요?

한 번 등록한 example.com 아래에 www.example.com과 api.example.com처럼 서브도메인을 만들 수 있습니다. 각각을 따로 구매하는 것이 아니라 DNS 레코드로 서로 다른 서비스에 연결합니다. 아래 이름은 구조를 설명하기 위한 예시입니다.

등록한 도메인: example.com
www.example.com→Vercel 프런트엔드 · 사람이 방문하는 화면
api.example.com→AWS EC2의 HTTPS API · Django가 요청 처리

이 프로젝트의 브라우저 요청은 프런트 주소에서 시작합니다. Vercel은 /api/*, /accounts/*, /_allauth/*를 API 서버로 rewrite합니다. Rewrite는 브라우저 주소를 바꾸지 않고 뒤에서 요청을 다른 서버로 전달하는 방식입니다.

화면 요청브라우저: www.example.com→Vercel이 페이지 응답
API 요청브라우저: www.example.com/api/…→Vercel rewrite→https://api.example.com→EC2 · Django
API 도메인도 중요합니다. 주소창에는 주로 프런트 도메인이 보이지만, Vercel은 API 도메인을 DNS로 찾고 유효한 HTTPS 인증서를 확인한 뒤 EC2에 접속해야 합니다. 이 구성에서 API 도메인은 단순한 내부 별명이 아닙니다.

일반적인 그림: example.com은 구조 설명용 예시이며 실제 이름은 DNS 레코드로 정합니다. TRACEBACK 사례: 프런트는 traceback-client-nine.vercel.app, 백엔드 API 이름은 api.dev-traceback.com입니다. API DNS A 레코드는 EIP까지 연결했지만, HTTPS 인증서와 Nginx·Django 앱은 아직 준비되지 않았습니다.

그림은 설명을 위한 대표 경로입니다. 실제 A 응답 IP는 위치·시점에 따라 달라지고, CNAME·AAAA 조회, DNSSEC, 전송 재시도 등으로 패킷 수가 늘 수 있습니다. 위임 응답의 IP(glue)는 조건에 따라 포함되며, 없으면 Resolver가 NS 이름의 주소를 별도로 조회합니다.
