DECISION 1 · 상태 전달

브라우저 세션 vs API 토큰

TRACEBACK 선택

서버 측 세션 + HttpOnly 쿠키

브라우저는 세션 ID를 쿠키로 보냅니다. 서버가 DB의 세션을 조회하므로 로그아웃·세션 종료를 서버에서 제어하기 쉽습니다. 브라우저 요청에는 CSRF 방어가 필요하고, 여러 서버에서 실행하면 공유 세션 저장소가 필요합니다.

선택 이유: 고객 프런트와 API 경로를 같은 Vercel origin으로 보이게 하고, Django DB 세션과 CSRF를 그대로 활용합니다.

대안

Access token · JWT 또는 불투명 토큰

클라이언트가 토큰을 API에 제시합니다. 모바일 앱·서로 다른 도메인의 API·서비스 간 호출에 맞출 수 있습니다. 브라우저 저장 위치, 만료·갱신·탈취·철회 정책을 별도로 설계해야 합니다. JWT는 토큰 형식이지 인증 시스템 전체가 아닙니다.

선택 조건: 독립 모바일 클라이언트나 다수 API가 실제로 필요한 경우 다시 비교합니다.

쿠키를 쓰면 CSRF는 왜 필요하고, HttpOnly는 무엇인가요?

브라우저는 같은 사이트 요청에 쿠키를 자동으로 붙입니다. CSRF는 사용자가 의도하지 않은 다른 사이트의 변경 요청을 막는 검증입니다. HttpOnly는 자바스크립트가 세션 쿠키 값을 직접 읽지 못하게 합니다. TRACEBACK의 변경 요청은 X-CSRFToken을 보내고, 배포 환경은 HTTPS와 secure cookie를 사용합니다. Django 세션 문서 · Django CSRF 문서

DECISION 4 · 외부 API와 DB 사이

탈퇴 중 Kakao는 성공하고 DB가 실패하면?

DB의 atomic()은 Kakao 서버까지 되돌리지 못합니다. 선택할 것은 “어느 쪽을 먼저 호출하나”만이 아니라, 중간 실패를 발견하고 끝까지 처리할 기록을 어디에 남기나입니다. 현재 TRACEBACK 코드는 이 복구 기록이 없습니다.

먼저 탈퇴 결과를 구분하세요. TRACEBACK은 User 행을 남기고 비활성·익명화하는 soft delete를 합니다. EmailAddress와 SocialAccount는 실제 삭제합니다. 이메일 전용 계정은 Kakao 호출 없이 내부 트랜잭션으로 끝낼 수 있습니다. Kakao 전용과 이메일+Kakao 계정은 둘 다 원격 unlink가 필요합니다. 세 계정 유형의 전체 탈퇴 그림

1 · DB 작업 기록 커밋탈퇴가 필요함을 잃지 않음
→
2 · Kakao unlink 성공외부 side effect 발생
→ 💥 →
3 · DB 완료 기록그 전에 죽으면 성공 여부가 남지 않음

작업 요청을 잃지 않는 것 ≠ Kakao를 정확히 한 번만 호출하는 것. ②와 ③ 사이에서 죽으면 상태 머신이나 outbox가 있어도 재시도 때 unlink를 다시 호출할 수 있습니다. DB 트랜잭션을 Kakao 호출 동안 열어 두어도 외부 성공 뒤 로컬 롤백은 막지 못합니다. 재시도는 외부 API의 멱등한 동작 또는 목표 상태 확인과 함께 설계해야 합니다.

① 상태 머신 + 재시도DELETE_PENDING을 커밋하고 실패·만료 작업을 다시 찾습니다. 원격 성공 뒤 DB 실패도 나중에 끝낼 수 있습니다.목표: 최종 수렴
② Transactional outbox / 작업 행계정 상태와 작업 요청을 같은 DB 커밋에 남깁니다. 큐 전달·worker 실행은 다시 일어날 수 있습니다.목표: 작업 요청 유실 방지
③ Kakao의 멱등성·상태 확인재호출 후 이미 연결 해제된 상태를 확인해 성공으로 수렴합니다. 외부 호출 횟수를 한 번으로 보장하지는 않습니다.목표: 중복 호출의 결과 안전성

SELECT FOR UPDATE, 조건부 UPDATE, SKIP LOCKED, DELETING 점유는 위 세 축과 별개의 원자성 해결책이 아닙니다. 여러 실행자가 동시에 같은 작업을 처리하지 않도록 하는 구현 도구입니다. 점유자가 외부 성공 뒤 DB 기록 전에 죽는 문제는 여전히 남습니다.

① 커밋된 계정 상태DELETE_PENDING부터 완료까지 로그인·변경을 막는 논리적 잠금
② 짧은 DB 행 락경쟁자가 작업을 가져가거나 완료 상태를 적을 때만 유지
③ 점유 토큰·만료동시에 처리할 실행자를 하나로 조정하고 멈춘 작업을 인수

상태 전이 vs outbox는 양자택일이 아닙니다. 상태는 계정·작업이 지금 무엇을 기다리는지 표현하고, outbox는 작업 요청을 DB에 내구성 있게 남겨 전달하는 패턴입니다. Celery는 실행기입니다. Outbox를 소비한 worker가 Kakao 성공 직후 죽으면 이벤트를 다시 소비하고 Kakao를 재호출할 수 있습니다. AWS transactional outbox 설명

TRACEBACK 현재 코드

원격 호출 → 로컬 DB 변경

코드가 적고 성공 경로는 즉시 끝납니다. Kakao 성공 뒤 DB 변경이 실패하면 원격 연결만 끊긴 채 복구 기록이 없습니다. validate_disconnect() 검증 단계에서도 외부 호출을 합니다.

Kakao Unlink에서 재시도를 안전하게 해석할 근거

가장 편한 형태는 외부 API가 같은 요청을 반복해도 결과가 하나로 수렴하도록 멱등성을 제공하는 것입니다. 2026-10-04 기준 공식 Unlink 요청 사양과 오류 코드를 대조했습니다. 아래는 공식 문서에 명시된 범위와 TRACEBACK 코드의 현재 처리입니다.

① Idempotency-Key공식 Unlink 요청의 헤더·파라미터에 요청별 멱등성 키가 문서화되어 있지 않습니다. 같은 키로 정확히 한 번만 처리된다고 가정할 수 없습니다.문서상 지원 확인 안 됨
② 연결 상태 확인Admin Key와 target_id로 GET/POST /v2/user/me를 호출하면 연결된 사용자의 정보를 조회할 수 있습니다. 전용 상태 조회 API는 아니며 오류 해석·권한 확인이 필요합니다.간접 확인 경로 있음
③ 이미 해제된 응답Kakao의 -101은 해당 앱에 연결되지 않은 사용자를 뜻합니다. 올바른 앱 키·대상 ID로 호출했다면 목표 상태인 “연결 없음”으로 해석할 수 있습니다.현재 코드도 -101을 성공 처리

타임아웃이면 결과가 모호합니다. 요청이 Kakao에 도착하지 않았을 수도, unlink는 성공했지만 응답만 사라졌을 수도 있습니다. 같은 앱의 Admin Key와 저장된 Kakao UID로 상태를 확인하거나 재호출해 -101을 목표 상태로 해석할 수 있습니다. 다만 이 과정은 최종 상태를 맞추는 방법이지, 외부 호출을 정확히 한 번만 보장하는 방법은 아닙니다. 현재 구현에는 타임아웃 뒤 상태 조회·작업 재시도 흐름이 없습니다. Kakao 사용자 정보 조회 사양

Celery 작업자같은 작업을 조회하고 claim 시도

요청이 작업의 DELETING 점유를 커밋합니다. Celery는 이미 바뀐 작업 상태를 보고 건너뛰며 Kakao를 호출하지 않습니다.

여기서 claim은 TX1과 TX2 사이의 별도 짧은 DB 트랜잭션입니다. 계정의 DELETE_PENDING을 숨기는 방식이 아닙니다. 두 실행자가 작업을 읽더라도 작업 행을 잠근 뒤 READY인지 다시 확인하거나 WHERE state = READY 조건부 변경을 하여 승자를 한 명만 정하고 커밋합니다. 패자는 변경된 작업 상태를 보고 중단합니다. 락은 Kakao 호출 동안 유지하지 않습니다.

Kakao 성공 → DB 완료 실패

원격 해제는 되돌릴 수 없습니다. DB에는 여전히 탈퇴 대기 작업과 점유 만료 시각이 남습니다.

만료 뒤 다른 실행자가 인수합니다. Kakao가 이미 해제됐다는 응답도 앱·대상 ID를 확인하며 다뤄야 합니다. 늦게 끝난 이전 실행자는 점유 토큰이 바뀌었으므로 DB 완료를 덮어쓰지 못합니다.

두 실행자가 동시에 READY를 읽으면 실제로 무엇이 일어나나요?

조회 자체는 둘 다 성공할 수 있습니다. 요청이 작업 행을 먼저 잠그고 READY → DELETING, 토큰 A, 만료 시각을 기록해 커밋하면 락이 풀립니다. 기다리던 Celery는 잠금 뒤 상태를 다시 읽고 DELETING을 확인해 아무것도 변경하지 않고 끝납니다. Celery가 먼저 잠갔다면 역할이 반대가 됩니다. 조건부 UPDATE ... WHERE state = 'READY' 방식도 변경된 행 수가 1인 실행자만 승자로 처리합니다. 두 방법 모두 읽었다는 사실이 아니라 DB의 원자적 변경 결과로 승자를 판정해야 합니다.

왜 Kakao 호출이 끝날 때까지 DB 행 락을 잡지 않나요?

행 락은 트랜잭션이 끝나면 풀립니다. Kakao의 네트워크 지연 동안 트랜잭션을 열어 두면 다른 DB 작업을 오래 막고, 프로세스가 죽으면 커밋하지 못한 DELETE_PENDING까지 롤백될 수 있습니다. TX1에서 DELETE_PENDING을 먼저 커밋하고, 별도 짧은 트랜잭션에서 점유를 커밋한 다음, 외부 호출은 락 없이 합니다. 탈퇴 완료 전 계정 차단은 DB 행 락이 아니라 DELETE_PENDING을 확인하는 애플리케이션 정책입니다. Django 행 잠금 문서

점유 중 실행자가 멈추거나, 만료 후 다시 살아나면요?

실행자는 점유 토큰과 만료 시각을 DB에 남깁니다. 만료된 작업은 다음 실행자가 새 토큰으로 다시 claim할 수 있습니다. 늦게 돌아온 이전 실행자가 TX2를 시도해도 토큰이 다르면 DB 완료를 거부합니다. 이 보호는 로컬 DB에만 적용됩니다. 이전 Kakao 호출이 실제 성공했는지 모르는 시간 초과나 만료 후 중복 호출은 여전히 가능하므로, “이미 해제됨” 응답을 대상 확인 후 성공 상태로 해석할 수 있는지 검증하고 오류 기록·재시도·수동 조사 경로를 마련해야 합니다. 점유 만료는 정상 호출의 제한 시간보다 충분히 길게 잡거나 연장합니다.

Celery의 on_commit 알림만 보내면 outbox가 필요 없나요?

on_commit은 DB 커밋 전 작업 실행을 막지만, 커밋 뒤 브로커 발행이 실패한 작업을 자동 복구하지 않습니다. 확실한 재처리에는 DB에 남은 작업을 다시 찾는 절차가 필요합니다. 별도 outbox 테이블을 둘 수도 있고, 계정 탈퇴 작업 행 자체를 내구성 있는 작업 기록으로 삼아 주기적으로 조회할 수도 있습니다. 중복 전달은 가능하므로 점유·만료·재시도와 멱등한 완료 처리가 필요합니다. Celery on_commit 설명 · AWS outbox 설명

현재 회원탈퇴 코드 · 복구 기록 없음

Kakao 로그인과 탈퇴는 같은 allauth 코드만 실행하나요?

아닙니다. Kakao OAuth callback과 연결 계정은 allauth가 다루지만, TRACEBACK 어댑터가 새 Kakao 연결의 verified email을 검사하고 검증 훅에서 원격 unlink도 요청합니다. 전체 계정 삭제는 서비스 코드가 원격 unlink 성공 뒤 User·연결·이메일을 DB 트랜잭션에서 정리하며 세션은 그 뒤 종료합니다. 현재 두 경로에는 외부 성공 뒤 로컬 실패를 복구하는 기록이 없습니다. 위 외부 API·DB 절에서 문제와 개선 선택지를 봅니다.
