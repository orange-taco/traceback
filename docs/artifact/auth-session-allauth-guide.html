로그인 상태는 어떻게 유지하고,
누가 가입 흐름을 맡을까?

세션과 토큰은 로그인 상태를 전달하는 방법이고, allauth는 가입·인증·계정 연결 흐름을 구현하는 라이브러리입니다. Headless는 allauth를 별도 프런트엔드에서 API로 쓰는 방식입니다. 서로 다른 선택을 한 번에 비교하지 않도록 층을 나눠 봅니다.

① 브라우저가입·로그인 요청
→
② 인증 흐름비밀번호·이메일·소셜 검증
→
③ 상태 저장User·이메일·세션
→
④ 다음 요청쿠키 또는 토큰으로 신원 확인

먼저 ④의 상태 전달 방식을 고르고, 다음으로 ②의 구현 방식을 비교합니다. 아래 초록색은 TRACEBACK 선택이며 다른 방식도 일반적으로 사용됩니다.

DECISION 1 · 상태 전달

브라우저 세션 vs API 토큰

TRACEBACK 선택

서버 측 세션 + HttpOnly 쿠키

브라우저는 세션 ID를 쿠키로 보냅니다. 서버가 DB의 세션을 조회하므로 로그아웃·세션 종료를 서버에서 제어하기 쉽습니다. 브라우저 요청에는 CSRF 방어가 필요하고, 여러 서버에서 실행하면 공유 세션 저장소가 필요합니다.

선택 이유: 고객 프런트와 API 경로를 같은 Vercel origin으로 보이게 하고, Django DB 세션과 CSRF를 그대로 활용합니다.

대안

Access token · JWT 또는 불투명 토큰

클라이언트가 토큰을 API에 제시합니다. 모바일 앱·서로 다른 도메인의 API·서비스 간 호출에 맞출 수 있습니다. 브라우저 저장 위치, 만료·갱신·탈취·철회 정책을 별도로 설계해야 합니다. JWT는 토큰 형식이지 인증 시스템 전체가 아닙니다.

선택 조건: 독립 모바일 클라이언트나 다수 API가 실제로 필요한 경우 다시 비교합니다.

쿠키를 쓰면 CSRF는 왜 필요하고, HttpOnly는 무엇인가요?

브라우저는 같은 사이트 요청에 쿠키를 자동으로 붙입니다. CSRF는 사용자가 의도하지 않은 다른 사이트의 변경 요청을 막는 검증입니다. HttpOnly는 자바스크립트가 세션 쿠키 값을 직접 읽지 못하게 합니다. TRACEBACK의 변경 요청은 X-CSRFToken을 보내고, 배포 환경은 HTTPS와 secure cookie를 사용합니다. Django 세션 문서 · Django CSRF 문서

DECISION 2 · 계정 흐름 구현

가입·이메일·소셜 인증은 누가 구현할까?

Django 기본 auth + 직접 API 작성

모델·세션 기반은 단순하게 시작할 수 있습니다. 대신 이메일 확인, 비밀번호 재설정, 소셜 연결·해제, 재전송 제한과 오류 흐름을 직접 구현·유지해야 합니다.

TRACEBACK 선택

django-allauth

가입, 이메일 확인, 비밀번호 관리, 소셜 계정 흐름을 한 라이브러리에서 다룹니다. 커스텀 User와 Django 세션을 함께 사용할 수 있습니다. 설정과 라이브러리 흐름을 이해해야 하고, Kakao 검증·삭제 정책은 프로젝트 코드로 추가했습니다.

외부 관리형 인증 · Cognito/Auth0 등

계정 운영과 일부 인증 기능을 서비스에 위임할 수 있습니다. 반면 외부 사용자 저장소·가격·콜백·앱 데이터 연결 정책이 추가됩니다. TRACEBACK의 초기 한 서버·한 웹 클라이언트에는 필요성이 확인되지 않았습니다.

dj-rest-auth 같은 DRF API 패키지

REST 로그인·비밀번호 endpoint를 빠르게 구성할 수 있습니다. 소셜 로그인·가입에는 allauth를 함께 쓰는 구성도 있어 두 도구가 항상 양자택일은 아닙니다. TRACEBACK은 allauth 자체의 Headless API가 이미 필요한 흐름을 제공해 API 래퍼를 추가하지 않았습니다. 패키지 설명

기본 템플릿 화면

Django가 로그인·가입 HTML을 직접 렌더링합니다. 단일 Django 웹앱에는 단계가 적습니다. 별도 React 프런트의 UX를 유지하려면 화면과 이동 경로를 맞춰야 합니다.

Headless browser API · 현재 방식

프런트가 화면을 맡고 allauth가 JSON 인증 흐름을 맡습니다. Kakao OAuth callback은 서버의 allauth.urls가 여전히 처리합니다. HEADLESS_ONLY=True는 기본 계정 화면을 숨기며 callback까지 없애는 설정은 아닙니다.

독립된 두 축: Headless를 써도 세션 쿠키를 쓸 수 있습니다. Headless가 JWT를 뜻하지 않습니다. allauth Headless 설정 문서

1
React Router가 같은 origin으로 요청가입은 POST /_allauth/browser/v1/auth/signup; 세션 조회는 GET /_allauth/browser/v1/auth/session.
2
Vercel rewrite → EC2 Nginx → DjangoDJANGO_ORIGIN이 인증 경로를 API 서버로 전달합니다. 배포 HTTPS가 준비되어야 이 구간이 통과합니다.
3
allauth가 계정·확인 메일·소셜 흐름 처리이메일은 확인 전 로그인 불가. Kakao 새 연결에는 verified provider email이 필요합니다.
4
Django 세션과 CSRF로 다음 요청 검증브라우저는 sessionid를 보내고, 서버는 DB 세션을 확인합니다. 계정 삭제·Kakao 연결 해제는 추가 프로젝트 정책을 거칩니다.

Kakao 로그인과 탈퇴는 같은 allauth 코드만 실행하나요?

아닙니다. Kakao OAuth callback과 연결 계정은 allauth가 다루지만, TRACEBACK 어댑터가 새 Kakao 연결의 verified email을 검사하고 원격 unlink를 요청합니다. 전체 계정 삭제는 서비스 코드가 원격 unlink 성공 뒤 User·연결·이메일을 DB 트랜잭션에서 정리하며 세션은 그 뒤 종료합니다. 분기 그림은 System Guide 인증 탭에 있습니다.
