# Traceback Simple Build Guide

이 문서는 TRACEBACK 백엔드를 실제로 구현할 때 먼저 보는 간단한 기준이다.
기존 상세 문서는 버리지 않고, 결정 배경과 후보 설계를 확인하는 참고 자료로 사용한다.

## 기본 방향

- TRACEBACK은 seller가 입점하지 않는 단독 브랜드 커머스다.
- 주문은 seller/merchant/vendor 단위로 쪼개지지 않는다.
- MVP에서는 `Order`와 `OrderLine` 중심으로 주문을 표현한다.
- 모델의 큰 역할과 관계는 먼저 정하되, 컬럼은 해당 Phase에서 필요한 만큼만 확정한다.
- 의류 도메인 특성상 상품 옵션, 사이즈, 색상, 재고 표현은 실제 브랜드 운영 방식에 맞춰 확정한다.
- 미래 확장을 이유로 현재 필요 없는 테이블, 컬럼, 상태값, API를 미리 만들지 않는다.
- 결제, 재고, 취소, 환불처럼 정합성이 중요한 영역은 단순하게 시작하되, 나중에 복구 불가능한 구조는 피한다.

## 문서 사용 방식

1. 새 작업은 이 문서에서 범위와 원칙을 먼저 확인한다.
2. 현재 작업을 빠르게 재개할 때는 [`current/README.md`](./current/README.md)를 확인한다.
3. 필요한 경우에만 기존 상세 문서를 참고한다.
4. 상세 문서에 있는 컬럼, enum, endpoint는 확정 명세가 아니라 설계 후보로 본다.
5. 구현 중 선택지가 갈리면 코드로 밀어붙이지 않고 사용자에게 질문한다.
6. 확정된 결정만 해당 Phase 문서나 코드에 반영한다.

## 구현 원칙

### 1. 단독 브랜드 기준

TRACEBACK은 하나의 브랜드가 직접 판매하는 구조다.

따라서 MVP에서는 다음을 만들지 않는다.

- seller 계정
- seller별 상품/주문 분리
- seller 정산
- seller별 배송 정책
- marketplace 권한 구조

필요한 관리자 권한은 Django admin 또는 단순 staff 관리자 API로 시작한다.

### 2. 이번 배포의 도메인 범위는 먼저 고정한다

PR 단위 구현은 작게 나누더라도, 이번 배포에서 완성할 도메인 범위는 미리 공유한다.
여기서 "이번 배포"는 현재 작업 Phase가 아니라 Phase 0부터 Phase 8까지 나누어 구현할
첫 MVP 릴리스를 뜻한다.

이번 배포의 목표 범위:

- 고객이 상품을 보고 장바구니에 담을 수 있다.
- 비회원 고객이 주문을 만들고 결제할 수 있다.
- 결제 성공 후 주문과 재고가 일관되게 반영된다.
- 관리자는 상품, 재고, 주문의 최소 운영 정보를 확인할 수 있다.
- 배송 전 전체 취소는 Phase 5에서 처리할 수 있다.
- 관리자 부분취소와 기본 환불 흐름은 Phase 7에서 처리할 수 있다.

이번 배포에서 제외하는 범위:

- seller/marketplace
- 회원 등급, 포인트, 리뷰, 찜
- 쿠폰/프로모션
- 교환
- 복수 창고/WMS
- 프리오더 고도화
- 복잡한 부분출고/부분반품 자동화

### 3. 모델은 역할과 필수 의미부터 정한다

모델을 만들 때는 먼저 역할과 관계만 확정한다.

예:

- `Product`: 판매 상품의 공통 정보
- `ProductVariant`: 실제 구매 가능한 옵션
- `Order`: 고객의 한 번의 주문
- `OrderLine`: 주문에 포함된 상품 옵션과 수량
- `Payment`: 주문에 대한 결제 시도 또는 결과

컬럼은 해당 Phase에서 화면, API, 운영 요구가 명확해진 뒤 정한다.
상세 문서의 컬럼 목록은 구현 시작 전 검토 자료로만 사용한다.

다만 모델이 반드시 담아야 하는 의미는 미리 정한다.

#### Catalog

`Product`는 판매자가 고객에게 보여주는 상품의 공통 정보를 담는다.

반드시 표현해야 하는 의미:

- 고객에게 보이는 이름
- 노출 여부
- 기본 가격 또는 가격을 계산할 기준
- 상품을 분류하거나 찾기 위한 식별 정보
- 상세 설명을 연결할 수 있는 정보

`ProductVariant`는 실제 구매 가능한 옵션 단위를 담는다.

반드시 표현해야 하는 의미:

- 어떤 상품에 속하는지
- 고객이 선택하는 옵션명 또는 옵션 조합
- 실제 판매 가격
- 판매 가능 여부
- 재고를 판단할 기준 수량

`ProductImage` 또는 이에 준하는 구조는 상품/옵션 이미지를 담는다.

반드시 표현해야 하는 의미:

- 어떤 상품 또는 옵션에 속하는지
- 이미지 URL 또는 파일 참조
- 대표 이미지 여부
- 노출 순서

#### Cart

`Cart`는 비회원 또는 고객의 주문 전 장바구니를 담는다.

반드시 표현해야 하는 의미:

- 장바구니 소유자 또는 익명 식별자
- 장바구니가 아직 사용 가능한지
- 만료가 필요하다면 만료 기준

`CartItem`은 장바구니에 담긴 구매 후보를 담는다.

반드시 표현해야 하는 의미:

- 어떤 장바구니에 속하는지
- 어떤 상품 옵션을 담았는지
- 수량

#### Order

`Order`는 고객의 한 번의 구매 의사를 담는다.

반드시 표현해야 하는 의미:

- 주문을 외부에서 찾을 수 있는 주문번호
- 주문자 정보 snapshot
- 배송지 snapshot
- 상품 금액, 배송비, 할인, 최종 결제 금액
- 주문 생성 시점
- 비회원 조회를 위한 접근 기준

`OrderLine`은 주문에 포함된 상품 옵션과 수량을 담는다.

반드시 표현해야 하는 의미:

- 어떤 주문에 속하는지
- 어떤 상품 옵션을 주문했는지
- 주문 시점의 상품명, 옵션명, 가격 snapshot
- 주문 수량
- 취소/환불/출고 판단에 필요한 수량 기준

#### Payment

`Payment`는 주문에 대한 결제 시도와 결과를 담는다.

반드시 표현해야 하는 의미:

- 어떤 주문에 대한 결제인지
- 결제사 또는 결제 수단
- 결제 요청 금액
- 외부 PG에서 주문/거래를 찾을 수 있는 식별 기준
- 성공, 실패, 처리 중을 판단할 수 있는 결과 기준

결제 webhook, 재시도, 환불처럼 세부 테이블이 필요한지는 Phase 4에서 확정한다.

#### Inventory

재고는 상품 옵션 단위로 판매 가능 여부를 판단할 수 있어야 한다.

반드시 표현해야 하는 의미:

- 어떤 상품 옵션의 재고인지
- 현재 판매 가능한 수량을 계산할 기준
- 주문 생성 또는 결제 성공과 연결해 중복 차감을 막을 기준
- 운영자가 조정 내역을 추적할 수 있는 최소 근거

초기에는 단순 수량 필드로 시작할 수 있다. 재고 이동 이력 테이블이 필요한지는 주문/결제 구현 시점에 확정한다.

#### Fulfillment / Refund / Return

출고, 환불, 반품은 이번 배포에서 최소 운영 흐름만 확정한다.

반드시 표현해야 하는 의미:

- 어떤 주문 또는 주문 라인에 대한 처리인지
- 처리 수량
- 처리 금액이 있다면 금액 근거
- 처리 상태
- 운영자가 사유와 시점을 확인할 수 있는 근거

세부 모델을 한 번에 확정하지 않고, 배송 전 취소와 기본 환불을 구현할 때 필요한 만큼 나눈다.

### 4. API는 필요한 순간에 확정한다

API 문서는 모든 endpoint를 미리 확정하지 않는다.

각 Phase에서 다음만 정하고 구현한다.

- 이번 Phase에 필요한 endpoint
- 요청 필드
- 응답 필드
- 인증 방식
- 대표 오류
- 테스트해야 할 핵심 동작

미래 Phase의 API는 후보로만 둔다.

### 5. 상태값은 최소로 시작한다

상태값은 UI와 운영에 실제로 필요한 만큼만 만든다.

특히 주문, 결제, 출고, 환불 상태는 서로 영향을 주기 때문에 처음부터 과하게 나누지 않는다.
다만 결제 완료 후 재고, 취소, 환불 정합성을 망가뜨리는 단순화는 피한다.

### 6. 재고와 결제는 되돌릴 수 있게 설계한다

MVP라도 다음 원칙은 유지한다.

- 결제 PG 호출은 DB 트랜잭션 안에서 직접 오래 잡고 수행하지 않는다.
- 주문 생성, 결제 완료, 재고 차감은 중복 요청에 안전해야 한다.
- 결제 결과가 애매하면 출고를 바로 진행하지 않는다.
- 수량과 금액은 나중에 감사할 수 있어야 한다.

구체적인 테이블과 컬럼은 해당 Phase에서 확정한다.

## Phase별 현재 기준

### Phase 0 - Foundation

목표:

- Django/DRF/PostgreSQL 기반을 만든다.
- 계정 API는 `/api/accounts` 기준으로 시작한다.
- 공통 오류 응답, pagination, request ID, 관리자 인증을 얇게 만든다.
- Custom User/Auth 기반을 만든다.
- Kakao/Naver 소셜 계정 연결, 이메일 변경 요청, 사용자 토큰, 혜택 중복 방지 ledger의 최소 모델을 만든다.
- 운영/개발 명령과 CI를 유지한다.

아직 하지 않는다:

- 커머스 도메인 모델 전체 구현
- 주문/결제/재고 상세 설계 구현
- 미래 관리자 API 전체 구현
- `SiteSetting` 구현. 공개 설정이나 배송 정책이 필요해지는 Phase 1 또는 Phase 3에서 다시 확정한다.
- `IdempotencyRecord` 구현. 주문/결제/관리자 명령 API가 시작되는 Phase 3 전에 다시 확정한다.

확정된 Phase 0B 기준:

- User는 `AbstractBaseUser` + `PermissionsMixin` 기반 custom User를 사용하고 email로 로그인한다.
- 관리자 REST API는 `/api/accounts/admin/` namespace와 JWT Bearer token + `IsAdminUser`를 기준으로 한다.
- `UserToken`은 이메일 인증 24시간, 비밀번호 설정 1시간, 비밀번호 재설정 1시간 뒤 만료한다.
- `EmailChangeRequest`는 24시간 뒤 만료하고 같은 user 기준 10분에 1회 요청을 허용한다.
- `BenefitClaim`은 원문 개인정보 없이 HMAC hash ledger로 장기 보관한다.

### Phase 1 - Catalog

목표:

- 상품을 고객에게 보여줄 수 있는 최소 모델과 API를 만든다.
- 의류 옵션 구조를 실제 브랜드 운영 방식에 맞게 확정한다.
- 상품 이미지, 가격, 노출 여부, 품절 여부를 표현한다.

결정이 필요한 지점:

- 상품과 옵션을 어떤 단위로 노출할지
- 색상/사이즈/핏/시즌 등 어떤 속성이 필요한지
- 재고를 옵션 단위로만 볼지, 색상 그룹 같은 중간 단위가 필요한지
- 상세 설명을 단순 text/html로 둘지, structured JSON으로 둘지

### Phase 2 - Cart

목표:

- 비회원 장바구니를 먼저 만든다.
- 같은 옵션의 수량 변경과 삭제가 가능해야 한다.
- 구매 가능 수량은 장바구니 담기와 주문 생성 시 다시 검증한다.

결정이 필요한 지점:

- 장바구니 token 저장 방식
- 장바구니 만료 정책
- 품절/가격 변경 시 고객에게 보여줄 방식

### Phase 3 - Order

목표:

- 단독 브랜드 기준의 `Order`와 `OrderLine`으로 주문을 만든다.
- 주문 시점의 상품명, 옵션명, 가격은 snapshot으로 남긴다.
- 주문 생성은 중복 요청과 재고 경쟁에 안전해야 한다.

결정이 필요한 지점:

- 주문 생성 시 재고를 예약할지 즉시 차감할지
- 주문 만료 시간을 둘지
- 배송비와 무료배송 기준을 어디에서 관리할지
- 비회원 주문 조회 token을 어떤 방식으로 만들지

### Phase 4 - Payment

목표:

- 최초 PG 하나를 붙인다.
- 결제 confirm과 webhook 중복 처리를 안전하게 만든다.
- 결제 성공 후 재고와 주문 상태가 일관되게 보이도록 한다.

결정이 필요한 지점:

- 사용할 PG
- 결제 수단 범위
- webhook을 동기 처리할지, 후속 작업을 비동기로 넘길지
- 결제 실패 후 새 결제 시도를 어떻게 만들지

### Phase 5 이후

Phase 5는 비회원 주문 조회와 배송 전 전체 취소를 다룬다.
Phase 6은 출고를 다루고, Phase 7은 관리자 부분취소와 기본 환불을 다룬다.
Phase 8은 반품을 다룬다.
취소, 환불, 출고, 반품은 실제 운영 방식이 더 중요하다.
각 Phase를 시작할 때 기존 상세 문서를 참고하되, 필요한 모델과 API만 다시 확정한다.

## 질문해야 하는 분기점

아래 상황에서는 구현자가 판단만으로 확정하지 않고 사용자에게 묻는다.
이 목록에 해당하지 않는 구현 세부사항은 resume 없이 계속 진행하고,
구현·검증·문서 갱신까지 완료한 뒤 결과를 보고한다.

- PR 리뷰 대응
- 비즈니스 또는 제품 선택사항
- 기술 스택, 아키텍처, 인프라 같은 기술 선택
- 사용자가 직접 처리해야 하는 외부 연동

위 범주의 예:

- 모델 컬럼이 브랜드 운영 방식에 따라 달라지는 경우
- API 요청/응답이 관리자 화면 구조나 고객 경험 정책을 사실상 결정하는 경우
- 재고 차감, 예약, 복구 방식이 운영 리스크를 바꾸는 경우
- 결제/환불 실패 처리 방식이 고객 응대 정책을 바꾸는 경우
- 외부 PG, 소셜 로그인 provider, 이메일/SMS 발송 시스템 설정이 필요한 경우
- 기존 상세 문서와 단순 구현 방향이 충돌하고 그 충돌이 제품 또는 기술 선택을 요구하는 경우

## 완료 기준

각 작업은 다음을 만족해야 완료로 본다.

- 이번 Phase에서 필요한 동작만 구현했다.
- 기존 상세 문서를 무비판적으로 그대로 구현하지 않았다.
- 결정된 모델, API, 테스트가 서로 맞다.
- 다음 Phase가 의존할 최소 계약은 깨지지 않게 정리했다.
- 남은 선택지는 문서에 후보 또는 질문으로 남겼다.
